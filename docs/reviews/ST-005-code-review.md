# Code review – ST-005: Manage team member accounts
Base: main · Commits: 13 · Date: 2026-09-29

Findings 5 and 6 were fixed on disk while this review was being written (uncommitted at the time of writing); they are kept in the table with their fix recorded. All team integration tests are green afterwards (`npx vitest run --project integration src/modules/team/` → 30 passed).

Reviewed against the context pack (`node .claude/skills/implement/scripts/story-context.ts ST-005`), ADR 0002/0004/0006, `CONTEXT.md`, `.claude/skills/engineering-conventions/SKILL.md`, the tdd and codebase-design skills.

**Accepted deviations, not findings** (recorded here so the next reader does not re-open them):
- BC-Team is generic in `docs/domain/events.yaml` (no aggregates, no events), so account management is module functions in `src/modules/team/accounts.ts` rather than `aggregateCommand`s: no journal entry, no `CMD-`/`EVT-`/`RM-` IDs, no version check (Better Auth's `team_member` has no `version` column, so HS-16 does not apply). Authorization is still server-side and in one place per function, and the concurrency rule is enforced in the database. The audit trail is a follow-up feature (`docs/stories/OPEN_QUESTIONS.md`, decided by the user 2026-09-29).
- The last-technician invariant is enforced in `applyChange` under `pg_advisory_xact_lock` inside the transaction. I checked the holes: `createAccount` is outside the lock but can only *add* technicians, and `activeTechnicianCount` is read inside the locked transaction, so the invariant cannot be violated — at worst a demotion is rejected conservatively. This is sound.
- `npm run verify` green, 11/11 scenarios traced, `check-language.ts` green. No `console.*` anywhere in the diff, no password in a redirect URL, no internal IDs or team member names on a visitor page.

## Verdict
**ready to merge** – no blockers: the scenarios are enforced server-side, the last-technician invariant is genuinely safe under concurrency, and authorization is checked in the module for every function. Finding #1 should still be fixed before `done`, inside this story.

The single most important finding: **#1 – scoping the `failed_login` sweep to one username leaves failed attempts for never-repeated usernames in the table forever, and nothing else ever deletes them** (no cron by ADR 0002), which turns a login-attempt spray into unbounded table growth.
