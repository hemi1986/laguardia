# Code review – ST-097: Choose a new machine's maintenance tasks when registering it
Base: main · Commits: 5 · Date: 2026-10-29

Checked against: ADR 0002, ADR 0010, HS-22, `events.yaml` (POL-RegistrationAppliesChosenMaintenanceTasks, CMD-ChangeMachinesOfMaintenanceTask rules, RM-MaintenanceTaskChoiceForMachine), `CONTEXT.md`, the engineering conventions (including the two new paragraphs), and the 12 scenarios. `check-language.ts` reports nothing new: all 16 warnings were already there before this story.

What holds up:
- The registration and its tasks run in one transaction. Collection still knows nothing of maintenance tasks: `registerMachineCommand` is unchanged, and the chosen tasks travel only in `policies` of the step input (HS-22). Maintenance exports the composed command (ADR 0010 option 3).
- The inner CMD-ChangeMachinesOfMaintenanceTask runs through `context.run`, which does its own authorization check. *Changed by* is the registering technician in the journal.
- Unknown, removed and doubly chosen tasks are rejected by the existing decision on the machine side, and that rejection rejects the whole registration.
- *Proposed for a new machine* is computed on read, inside Maintenance, and leaves out retired machines (`machinesForMaintenance`).
- The two new convention paragraphs describe the code as it is (`run` vs `trigger`, `withPolicyInput`, `{ command, policies }`, `proposed` on `GroupedChoice`, `untickMaintenanceTasks`). The one exception is the stale reference in finding 2.
