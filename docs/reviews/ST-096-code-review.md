**Verdict: fix blockers first.**
Most important: #1. After a "removed meanwhile" rejection the JavaScript form does not refresh, so the removed task stays offered and ticked. The page test (#2) hides this because it reloads the groups itself instead of going through the Server Action.

## Resolution (implementing session, 2026-10-27)

- **#1 (blocker) – not reproduced.** Every Server Action re-renders its page (engineering conventions, *Server Actions and forms*), so the groups are fresh after a rejection. Checked in the browser: the new test "a task removed meanwhile rejects the change and is no longer offered in the browser" (`e2e/maintenance-plan-machines.spec.ts`) passes – the removed task is gone from the form, the other tick is kept. No `refresh()` needed; #8 (ST-095) therefore needs no change either.
- **#2 (major) – covered by the same browser test.** `changeTasksAction` imports `next/*` and cannot run in Vitest; the browser test drives the real action (name lookup, redirect, museum number).
- **Skipped minors:** #3 (naming a removed task that did not cause the rejection is still true and helps the technician), #4, #5 (an app test may not import the module's `MAINTENANCE_PLAN_ID`), #6, #7, #9 (fine at museum scale). **#10:** the `?tasksChanged=1` exception is named in the pull request for the user's approval.
