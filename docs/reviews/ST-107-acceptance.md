## The full local e2e suite – judgment for the gate

My `npm run test:e2e` (4 workers) ended **276 passed, 1 failed, 1 skipped**. The failure is `e2e/retired-machines.spec.ts:30`: `pageWidth` measured **589 > 360** on the machines list. It passes alone (2/2), and it is a shared-data/order effect, not this branch: the list shows ~190 machines created by the whole run, and the width is measured over the whole page, so a long unbroken model title or another spec's data can overflow the layout. The failing spec and page are untouched by ST-107 (no file in the branch diff is under `src/app/(team)/team/machines` or `e2e/retired-machines`). The user's 4-worker/2-worker runs had the same shape (file-upload progress, job-first, one-shape, retired-machines), every failing spec passes alone, and none touches AI assessments or the defect page. One earlier full run lost the dev server (`ERR_CONNECTION_REFUSED`) – environmental.

**Judgment:** this is not a blocker of ST-107 – the story's own scenarios, its no-JavaScript spec, the serial AI/settings pair, the unit/integration suite, `verify.ts` and the build are green, and the failure is an existing shared-e2e isolation/timing problem on a page this branch does not change. But it must not be reported as "`verify -- --e2e` green": the full suite is only 276/1/1 on this machine, and the same order-dependent failure can redden CI. Open a separate tech task for e2e stability (e.g. run the width-sensitive list specs serially, reset the browser DB per file or per worker group, or make the width assertion per entry), and re-run the full suite there. The branch itself does not need to be blocked on it.
