# Code review – ST-085: Direct private large-file upload and abandoned uploads
Base: main · Commits: 11 · Date: 2026-10-18

Checked: `git diff main...HEAD` (38 files), the context pack, ADR 0002/0006/0007/0009, `CONTEXT.md`, the engineering conventions (updated in this branch). `npx vitest run src/upload src/app/api/uploads src/platform/storage`: 5 files, 31 tests green. `check-language.ts`: 15 warnings, 8 of them from this branch ('pending', 'abandoned'). The browser tests were not run here because they need the Development Blob store.

Overall: the module is placed well. The boundary is enforced by lint, the route has its own Origin and session checks (both asserted), the size limit is a parameter of the seam, attaching and cleanup take the same record with a row-level delete as ADR 0009 requires, and the injected clock and ID generator are used everywhere. `isSameOrigin` is shared between the proxy and the route, which is a good refactoring.

Not findings (checked):
- Module boundaries: `src/upload` imports no module, other code reaches it only through `index.ts` / `browser.ts` (lint rules added), and foreign keys to other modules' tables are hand-written as the conventions require (ADR 0002).
- Security: Origin and session are checked before the body is read. The name is issued per team member and the address only to that member, valid 30 minutes, `allowOverwrite: false`. There are no completion callbacks, and the log line holds only the content name. The check page and its Server Action are technicians-only and unlinked, as the user decided on 2026-10-18.
- The stricter size limit from the request is capped at `FILE_SIZE_LIMIT` (asserted), as the user decided on 2026-10-18.
- `recordPendingUpload` is not a domain command (no ID, no journal). ADR 0009 decides it as technical state, so this is consistent with ADR 0002.
- Unticked AC (100 MB from a phone on the preview, the security-header browser test on the preview, the user's approval of the conventions) belong to the PR and acceptance steps.

**Verdict: ready to merge** (no blockers; fixing the major finding is a matter of documentation and comments, well within an hour).
Most important finding: #1 – Blob does not enforce the upload address's size limit for multipart uploads, which contradicts accepted ADRs 0006/0009 and ticked AC 4. The code compensates when attaching, but the deviation has to reach the user and be recorded where the decision lives.

## Resolution (main session, 2026-10-18)
- **#1 (major)** – fixed in the code, decision with the user: the storage seam's `uploadAddress` comment now says Blob holds only an upload in one piece to the limit; the PR states criterion 4 that way; the deviation from ADR 0006/0009 is a row in `docs/stories/OPEN_QUESTIONS.md` (recommendation: no new ADR – the size check when attaching closes it). Not tried: issuing `multipart: false` for small limits – the 100 MB files need parts.
- **#2** fixed – the in-memory adapter's `upload(…, { multipart: true })` is not held to the limit, like Blob; the `too-large` test uploads in parts.
- **#3** fixed – the size check runs inside the delete-on-failure path; a failing `size` deletes the content (new test).
- **#4** fixed – one boundary `abandonedUntil(now)` in `limits.ts`, used by attaching (younger) and the cleanup (at or before). Exactly 24 hours counts as abandoned – deliberate, the two sides only need to be complementary.
- **#5** skipped – running the scheduled cleanup in the route test would delete other test files' pending uploads in the shared database; the cleanup itself is proven in its isolated test.
- **#6** fixed – `contentName` / `isContentName` in `limits.ts`.
- **#7** fixed – **Pending upload** in `CONTEXT.md` as a technical term.
- **#8** revisit with ST-063 (dependency routine): the faked issuing body for `handleUploadPresigned` and the "File is too large" message match are the two places a `@vercel/blob` upgrade can break silently – the browser tests catch both.
- **#9** added to ST-037's notes.
