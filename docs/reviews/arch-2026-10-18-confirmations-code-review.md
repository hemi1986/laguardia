# Code review – arch-confirmations: one rule for confirmations (G3)
Base: main · Commits: 3 · Date: 2026-10-18

Refactoring branch from architecture review 2026-10-18, candidate 2 (no story). Checked: `lastCommandBy` against the
command layer (`src/platform/command/index.ts` – row order in `runInTransaction`, one `db.transaction` per
`executeCommand`), the migration against the append-only trigger (`drizzle/0001_…sql`: statement-level
`BEFORE UPDATE OR DELETE OR TRUNCATE`, so `ALTER TABLE … ADD COLUMN` does not fire it), the old-row fallback, policies
as the system actor, concurrent commands, the test changes, module boundaries and naming. `check-language.ts` reports no
warning in the changed files.

Correct as built: the actor check holds, because `runInTransaction` puts the command's own events (the acting person)
before the rows of `run` (same person) and `runAsSystem` (system). Splitting the migration into `ADD COLUMN` and then
`SET DEFAULT` really leaves old rows null: a non-volatile default in `ADD COLUMN` would give every old row the
migration's xid. `pg_current_xact_id()` is the 64-bit xid8, so it does not wrap around. Both queries in `lastCommandBy`
can run outside one snapshot without harm, because the journal is append-only and a committed transaction's rows never
change. The tests change only where behaviour changed on purpose. `defect-details.integration.test.ts` drops the
`statusChanged` flag, and the reopen now really changes the status. `triage-confirmation.integration.test.ts` covers
everything `triaged-when-reporting.integration.test.ts` covered, and adds the viewer binding and a real status change.
