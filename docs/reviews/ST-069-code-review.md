Most important finding: #1 – the "unknown" and "tampered" cookies are rejected by Better Auth's cookie format check before any signature or session lookup, so the test does not prove that a forged session is treated like no session.

## Resolution (implementer, 2026-10-01)

- **#1 major – fixed.** "Unknown" is now a correctly signed cookie whose session was ended (`logIn` → `logOut`); "tampered" changes one character of the session token and keeps the signature; `signedIn` asserts exactly one cookie. Checked by temporarily instrumenting `better-call`'s `getSignedCookie`: every cookie of the test reaches `verifySignature` with a 44-character signature (instrumentation removed).
- **#3 minor – fixed.** The Team module, which owns sessions, now ends the deactivated account's session itself before throwing `DeactivatedAccount`; the app adapter only redirects. The throw stays (one narrow catch, and `redirect()` throws anyway).
- **#5 minor – fixed.** `currentPerson()` (Team and app) and the conventions say: Server Actions only – ending a session sets a cookie.
- **#2 minor – skipped.** Accepted by the story: `deactivateAccount` deletes the sessions, so a later post with the old cookie is a visitor's, as decided in the story review of 2026-09-27 ("after the session has ended they can report as a visitor"). The branch is defense in depth for a session that survives.
- **#4 minor – skipped.** Pages send a deactivated account to `/login` without ending the session; they can't set a cookie while rendering, and the next Server Action ends it. Revisit if a page ever acts on the session.
- **#6 minor – skipped.** The expired case is anchored at a fixed date 4 months back and the 90-day length from ST-004; both stable.
- **#7 minor – skipped.** The redirect assertion matches Next's digest format; revisit on a Next.js upgrade if it breaks (the behaviour is also covered by the "session ended" assertions after it).
- Acceptance remarks: #1 (cookie removal) needs no check – `logOut` deletes the session row, so a kept cookie is an unknown session (visitor), not a deactivated one; #3 (no explanation on `/login`) skipped as a UX minor for a rare case.
