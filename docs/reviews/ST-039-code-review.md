# Code review – ST-039: Retire a machine, closing its open defects and problem reports
Base: main · Commits: 12 (up to 5801649) · Date: 2026-10-23

Reviewed: `git diff main...HEAD`, the context pack, ADR 0002, ADR 0010, the engineering conventions. The ST-039 integration tests and the adapted tests of other stories pass locally (14 files, 86 tests). `check-language.ts` reports only warnings that were there before (none in ST-039 code).

**The working tree changed while this review ran** (uncommitted, not by the reviewer): the reopening page read moved to `machineForReporting(…, { inCommand: false })`, the link command uses a new `holdAgainstRetirement`, Collection exports `retireMachineCommandWithoutPolicies`, the ask step checks `retireRefusal`, the `maintenanceFacts` comment and the OPEN_QUESTIONS row were fixed. Findings below are against the committed HEAD. Where the working tree already deals with one, the last column says so.

Lock design checked and sound: the retirement loads the machine without a row lock, takes the advisory lock exclusively in its facts, and only then updates the machine row and selects defects and problem reports `FOR UPDATE`. Every guarded command (report, record defect, reopen, link, record maintenance) takes the shared lock before any row lock of its own. No command that holds a defect or problem report row lock waits for the machine row or the advisory lock afterwards, so I found no deadlock path. `CMD-CloseDefectOnRetirement` has to end the hold (`defect_hold_only_open`). Migration 0027 is additive: a nullable column plus a check that no existing row can break, because no `closed-on-retirement` defect could exist before this story.

No blocker found. Checked and fine:
- Module boundaries: Repair imports only Collection's `index.ts`, and nothing in Collection names Repair.
- The command layer: one transaction, policies run as the system, journal `data` without the reason.
- IDs: `CMD-RetireMachine`, `CMD-CloseDefectOnRetirement`, `CMD-DismissProblemReport`, `POL-RetirementClosesDefects`, `POL-RetirementDismissesProblemReports`, `EVT-MachineRetired`, `EVT-DefectClosedOnRetirement`.

- Scope: `machineIdOf(…, { retiredToo })` is what the repair-history scenario needs.

**Verdict: ready to merge** (no blockers; fix the three majors in this story – about an hour together, so none passes the follow-up hurdle).
Most important finding: #1 – `withPolicies` gives a policy `{ result, actor }` instead of the triggering command's state and events that ADR 0010 decides. That is the precedent for every later cross-module policy, so align the code or get the user's decision now.
