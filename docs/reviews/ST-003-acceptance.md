## Edge cases and gaps

| Case | Expected by a rule? (cite) | Recommendation |
|---|---|---|
| The event journal stores the visitor's raw `description` in `data`, and the journal can never be updated or deleted (trigger). `AGG-ProblemReport`'s own invariant says "A problem report dismissed as spam has no description and no photo" – but once `CMD-DismissProblemReport` triages a report as spam, the *aggregate* loses the text while the already-written `EVT-ProblemReported` journal entry keeps it forever. This is the same issue the code review already flagged as a **blocker** (`docs/reviews/ST-003-code-review.md` #1); I found it independently before reading that report, which corroborates it. | Yes – `docs/architecture/data-model.md` invariant "dismissed as spam has no description and no photo"; DoD "no personal data in logs" is the same spirit applied to the journal. | Fix now, before more commands copy this pattern (the code review already recommends this): keep free text (descriptions, notes, photos) out of journal `data`; the journal should hold references/facts, read models join the aggregate for text. This is foundational – every later command will imitate whatever `CMD-ReportProblem` does. |
| `executeCommand` silently accepts a command whose `run` returns `ok: true` with an **empty** `events` array – nothing stops a future command from forgetting to emit its event, quietly breaking the DoD rule "every command writes its journal entry". | Implied by DoD, not an explicit rule | Question / minor: consider asserting `events.length > 0` in `executeCommand` (or an explicit, tested exception for read-only commands if any exist), so a forgotten journal entry fails loudly in tests rather than passing silently. |
| The append-only trigger (`event_journal_append_only`) is only exercised by hand (I confirmed manually with `docker exec … psql` that UPDATE, DELETE and TRUNCATE are all rejected) – there is no automated test for it, even though the checklist cites it as evidence. | No rule violated (it works), but the checklist claims a specific mechanism as evidence | Recommendation: add a short integration test that attempts an UPDATE/DELETE on `event_journal` and asserts it throws – cheap insurance against someone dropping the trigger in a later migration. |
| `x-forwarded-host` is trusted as-is in `src/proxy.ts` without pinning it to a known origin/allow-list; on Vercel this header is set by the trusted edge and can't be spoofed by a client, but the code itself doesn't document or assert that trust boundary. | Not a stated rule; a question | Question: worth a one-line comment (or an explicit allow-list of hosts) so a future reader doesn't assume `x-forwarded-host` is attacker-controlled input to sanitize, or conversely doesn't miss that it *would* be attacker-controlled off Vercel. |
| Only one command (`CMD-ReportProblem`) exercises the command layer; there is no test yet for a *team member from a foreign/wrong team* or a *retired/"not on display" machine* rule, but the story's Out of Scope explicitly excludes "any domain command beyond the test command of ST-001", so these belong to later stories (ST-013, ST-015, ST-018 ff.), not here. | Out of scope, explicitly | No action for ST-003. |
| The `system` actor is only ever tested as being *rejected* (when not allowed); no test yet shows a command *succeeding* as `system` and being journaled as such, since no automatic policy command exists yet. | Out of scope (no policy commands built here) | No action for ST-003; worth returning to when the first policy (e.g. `POL-RetirementClosesDefects`) is built, to confirm the actor round-trips through `journalOf` correctly (the plumbing – `journalActor()` – already handles `system`/`visitor` without a team member ID, and is exercised implicitly by `journalOf` on the visitor case). |
| No test shows what happens to `problem_report.machine_id`/`reporter_team_member_id` (still `text`, not `uuid`) if a bogus/non-UUID string is passed as `machineId` to `CMD-ReportProblem` – it would simply be stored, since there is no FK yet. | Expected – `OPEN_QUESTIONS.md` (ST-065 decision) explicitly defers the FK/column alignment to ST-007/ST-004 | No action for ST-003; already tracked. |

## Verdict
**Accepted with remarks.**

All ten checklist items have real, passing evidence (verified locally: `npx vitest run` – 69/69 passed; `verify.ts` – lint, typecheck, traceability all green; and via CI – both e2e/security.spec.ts scenarios pass against the real Vercel preview). The command layer, time helper, module boundaries, message catalogs and CSRF/security-header setup are all correctly built and match the story's cited decisions (`OPEN_QUESTIONS.md`, ST-043's overdue example, `CONTEXT.md`'s glossary wording) word for word.

The one substantive concern – free text permanently stored in the append-only event journal, conflicting with the "dismissed as spam has no description" invariant and the spirit of "no personal data in logs" – is not a new finding: it is already recorded as a **blocker** in `docs/reviews/ST-003-code-review.md` (#1), and I confirm it independently. It should be fixed in the refactor step before this branch is merged, since every future command will otherwise copy the same pattern. The remaining items (untested trigger, empty-events guard, `x-forwarded-host` trust) are minor remarks/questions, not rule violations.
