### Checked without findings
- **Load → decide → save.** The decision runs on the freshly loaded state, then the row is saved with `WHERE version = <seen>`. Two concurrent commands: the second update waits for the row lock and then matches 0 rows, so the result is `version-conflict`. The domain rejection comes before the conflict (Q11). There is an inherent race: if the second load happens before the first commit, the result is `version-conflict` instead of the domain rejection. That is acceptable and doesn't need documenting.
- **Created aggregates and rollback.** Created aggregates are inserted *before* the version-checked update, so the rollback test is real (`problem-report-version…:80`). Policies run after the save and journal after the command's own events.
- **Casts.** The `as never` casts in `aggregateStore.insert/update` are confined to generic Drizzle glue, and `toRow` is typed against `$inferInsert` at the definition, so they are acceptable. The cast in `created` is sound because the store and the state are bound together at construction. The cast in `trigger` is the one that loses information (#1).
- **Assertions carried over, old → new.** No assertion was lost:
  - Platform "rejected-after-writing" → split + version conflict (`version…:80`) and rejected policy (`policies…:36`).
  - Both policy tests → `problem-report-policies…`.
  - Concurrency and `not-found` → kept (`version…:32`, `:64`).
  - Decision tests → `report-problem.test.ts`, now also covering the acting team member.
  - Journal without description → `report-problem-command…:51`, plus the platform test at `:20`.
- **Journal and security.** The journal still holds no free text (`data: {}`). There is no `new Date()` or `randomUUID()` in decisions, and module boundaries hold: Repair's stand-ins live in Repair, and the platform test uses an in-memory store.

**Verdict: ready to merge** once the two majors are fixed. There are no blockers.
Most important finding: #2. The version the user saw is optional for every changing command, so HS-16's lost-update protection depends on each future command remembering to pass it.
