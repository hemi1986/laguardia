## Checked, no finding
- **Entry labels unchanged on every page.** Stickers: `machineEntryLabel(machine)` gives `LG-042 · Title`, as before. Maintenance-plan choice (adding a task, changing its machines): `· Nicht ausgestellt` is added only when the flag is set, as before. Recording for several: `· <location>`, the same as the old `entry(…, location)`, because `machine.location` is `notNull` and the register and move commands reject an empty location after trimming (`register-machine.ts:90-91`, `move-machine.ts:34-35`), so `filter(Boolean)` never drops it. The task choices (change a machine's tasks, registering with tasks) get no new labels; only the wrapper changed.
- **Order.** The group „Fällig“ still comes from `dueOn` → `dueMaintenance` sorted by `byLocation` (`due-maintenance.ts:121`), so it is the due list's order, unchanged. The further machines are regrouped by `groupMachines`, which sorts by museum number inside a group (`machine-groups.ts:25`). What the page shows was already in that order before; the dropped `byLocation` sort had no visible effect. `others` is read elsewhere only through a `Map` (`record-for-several-form.tsx:74`), so its order does not matter there. `byLocation` remains used inside `due-maintenance.ts`; it is not exported from the module index.
- **`TeamGroupedChoice`.** It is typed as `Omit<ComponentProps<typeof GroupedChoice>, "header" | "selectAll">` and spreads every other prop, so `proposed`, `open`, `openWithChoice`, `onChosenChange`, `chosen`, `name` and `groups` all pass through, and `key` stays on the element. It has a `"use client"` directive, and so does every caller (the four forms, `sticker-choice.tsx`, `record-for-several-form.tsx`). The header function is created on the client, so no function crosses the server/client line. The deletion test passes: without the wrapper, the two texts would come back in six call sites.
- **`due-maintenance.integration.test.ts` call changes.** `maintenanceForSeveral` takes `teamMember: { role: Role }`. The dropped `id` was only accepted by the deleted pass-through's `Viewer` type and never read. The calls go through Maintenance's public interface, and the assertions are unchanged, so this is not a weakening.
- **Removal of `record-for-several-data.ts`.** It was a pure pass-through (deletion test: nothing comes back). The page now calls Maintenance's public `maintenanceForSeveral` directly, which keeps the module boundary (ADR 0002).
- **Language.** `check-language.ts` reports no warning in the touched files. The new text `teamMessages.groupedChoice.machine` sits in the team message catalog.
- `RM-MachineChoiceForMaintenanceTask` still returns its groups, consistent with `events.yaml`.

**Verdict:** ready to merge – there are no blockers; findings 1 and 2 should still be fixed on this branch, each in a few minutes.
**Most important finding:** #1 – the ST-045 test pins the order of `others`, which the module no longer guarantees, so it now passes only because the database returns rows in insertion order.
