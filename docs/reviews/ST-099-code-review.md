| 1 | major | Architecture / test quality | `src/platform/storage/s3-storage.ts:104`, `:116-142` | `lastingCredentials` is how the adapter meets ADR 0012's consequence that an address signed with OIDC credentials must not outlive them. It has **no test**, although it is exported only for tests and the SeaweedFS tests use static keys and never reach it. It is also **fragile**: the SDK wraps any credential function in `memoizeIdentityProvider` (`@aws-sdk/core` `normalizeCredentialProvider`, `@smithy/core`), which asks the function again only when the cached credentials have **less than 5 minutes** left. The 35-minute rule only works because every request builds a new `s3Storage()` and so a new `S3Client`. An `S3Client` kept for longer (an obvious optimisation) would sign 30-minute upload addresses with credentials that have 5 minutes left, which is the case this code exists to prevent, and no test would notice. This rule is part of the adapter's interface but is written down nowhere. | ADR 0012 (Consequences: "the role's session must outlast the 30-minute upload address (checked in ST-099)"); tdd (untested logic); codebase-design (an interface fact hidden from callers) | Mark the provider `lastingCredentials` returns as already memoized (`memoized = true`; `normalizeCredentialProvider` then uses it as it is), so the 35-minute rule holds however long a client lives. Add a unit test with a fake `assume` and `now`: it reuses credentials while more than 35 min are left, renews below that, and renews after a failed attempt. Ideally also one test showing that a single `S3Client` signs with renewed credentials once time has passed. |

Most important finding: #1. The 35-minute credential renewal has no test and only works because every request builds a new S3 client. Mark the provider as memoized and test it, so an upload address can never outlive its credentials.
