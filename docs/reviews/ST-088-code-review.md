Checked without finding:
- **Every rejection is decided before writing.** `editedAccountRejection`, `changeRefusal` (deactivated, own role/password/deactivation, last technician) and the username check all run inside the transaction before the first `UPDATE`. A concurrent duplicate username is caught by the unique index and rolls back. The password is written in the same transaction, which is stronger than the story note assumed, and the conventions document it.
- **The ST-005 test changes are a legitimate new set-up, not a weakened test.** ST-005's "The last technician cannot lock the team out" requires only "Then the change is rejected". It still checks that, and that Tom stays the only active technician. Since ST-088, a non-concurrent `last-technician` refusal can no longer occur: the acting technician is always one more active technician, so the last one can only act on their own account and meets `own-role`/`own-deactivation` first. The `last-technician` branch stays covered by the two concurrency tests (ST-005 and ST-088), which assert exactly that error for the loser.
- **Superseded ST-081 scenarios.** The eight entries in `superseded-scenarios.json` match the tests that were removed. The kept ST-081 tests ("activates again", "deactivated account's page", creation, helpers) still run.
- **Sessions.** `cookieCache` is disabled in `auth.ts`, so deleting `session` rows ends sessions at the next action. A username change keeps sessions, and a new password ends them (both tested).
- **Security.** Authorization is checked in the Team module (`isTechnician`), the actor comes from `currentPerson()`, the new password is never echoed back (`EditAccountState` has no password), there are no logs, and the old `/deaktivieren` address only redirects.
- **Language.** Terms follow `CONTEXT.md` (Account/Konto, Team member/Teammitglied, Techniker:in, Helfer:in).

**Verdict: ready to merge.** No blockers. Fix the major finding in this story.
Most important finding: #1. Writing the password directly bypasses Better Auth's 128-character maximum, so an over-long password ends the team member's sessions and then can never be used to log in.
