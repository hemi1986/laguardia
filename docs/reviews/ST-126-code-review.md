# Code review – ST-126: An AI model proposal that fails or breaks off says why
Base: main · Commits: 2 · Date: 2026-11-08

Scope of the diff: the failing half of CMD-WriteAiModelProposal (`failAiModelProposal`, `failAiModelProposalCommand`,
`deviceRecognised`), the run's failure paths and `recordBrokenOff` in `ai-model-proposal-work.ts`, EVT-AiModelProposalFailed
in the event catalogue, `failure_reason` column + migration 0050, the failed view on the proposal page, „Nochmal versuchen“
via `?retry=<id>` on „Mit KI erstellen“, and tests (4 scenario tests at the run/page seam, decision unit tests). The
story's tests pass locally (28/28).

Focus passes (as requested):

- **Failing half / break-off / late result / hold:** I found no bug. Every failure goes through `piece.storeResult`, so it
  is stored only while this run still holds the piece (the hold is deleted in the same transaction). The break-off is
  recorded by `failOneBrokenOff`, which drops the hold in the same transaction, so the late run's `storeResult` returns
  `no-longer-held`. `failAiModelProposal` also rejects anything that is not *requested*: a second guard, through the
  locked load of `aggregateCommand` (no version, so the row is loaded with a lock). A rejection comes back as
  `{ok:false}` instead of an exception, so the hold is still ended and nothing loops. This is the same pattern as
  `failAiAssessmentCommand` (ST-108). The scenario test checks the journal (`Requested`, `Failed` only) and that no later
  run takes the proposal again.
- **`retry` parameter:** `requireTechnician()` runs before anything is read. The description is shown only to
  technicians, who can already open any proposal's page by its ID, so nothing new is exposed. An unknown proposal and a
  proposal that is not failed both give the same result, so the parameter tells an outsider nothing. Arrays are
  rejected, the query is parameterised, React escapes `defaultValue`, the address carries only the ID and no command
  runs on GET (no CSRF surface). One robustness gap remains (#3).
- **Migration 0050:** one additive, nullable `ALTER TABLE … ADD COLUMN "failure_reason" text`. It is safe on existing
  rows: ST-124 never produced a *failed* row, and proposals that ST-124 gave up on are still *requested* and are now
  failed or written by the next run. The `0050_snapshot.json` differs from 0049 only in id/prevId and the new column, and
  the journal entry idx 50 is in order. Like 0047–0049 it adds no CHECK for "only a failed one has a reason" (#8).
