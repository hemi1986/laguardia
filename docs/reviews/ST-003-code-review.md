Checked: `git diff main...HEAD`, the context pack, ADR 0002, `CONTEXT.md`, the data model, events.yaml (CMD-DismissProblemReport, HS-16), and the stories that will use the helpers first (ST-043, ST-056). | 2 | major | Architecture (policies) | `src/platform/command/index.ts:37,67-93` | There is no supported, tested way to run an automatic policy synchronously in the same transaction as the *system* actor, although ADR 0002 and the task require it (e.g. retirement closing defects). `CommandContext` has one actor, and `JournalEvent` cannot say "this event was the system's". The only workaround is to call `executeCommand(other, input, { actor: system, db: tx })` inside a command, which silently becomes a savepoint. Its `{ ok: false }` does not abort the outer command, and the clock and ID generator have to be passed by hand. Each policy story would end up inventing its own variant, and the conventions skill is written from this story. | ADR 0002 "Automatic policies run in-process and synchronously, in the same transaction"; story task bullet "Automatic policies … act as the *system* actor"; Shotgun Surgery | Add one policy seam to the command context now, e.g. `context.runAsSystem(command, input)`. It runs another module's command (imported through its `index.ts`) inside `tx` with the system actor, the same frozen clock and the same ID generator, and a rejection aborts the whole command. Cover it with one integration test: the journal shows the triggering event with the team member and the policy's event with the system, and a rejected policy stores nothing. |

| 8 | minor | Time helper interface | `src/platform/time.ts:59-66` | `maintenanceDates(lastDone, intervalMonths)` works out the grace days from `lastDone → dueDate`, which fits ST-043. It is also a Maintenance rule living in the generic platform. The doc comment says overdue once the date "is reached". Do not measure from the due date, which would give 8 for the February example. Put the maintenance-specific composition into the Maintenance module when ST-043 lands. Test quality is good overall. The tests sit at the agreed seams (`executeCommand`, `journalOf`, `problemReportsOfMachine`, eslint's public API, the e2e forged post). They verify through public interfaces rather than by querying tables. The expected values are independent literals (e.g. 3 April / 92 days from ST-043), the message test checks against `CONTEXT.md`, and the concurrency test really runs two transactions in parallel (pool of 2).

fix blockers first
Most important: the append-only journal stores visitor free text (#1), so the spam-dismissal rule and erasure of personal data can never be honoured. Decide what goes into journal `data` before any real entries are written.
