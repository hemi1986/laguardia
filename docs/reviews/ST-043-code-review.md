# Code review – ST-043: Due maintenance list grouped by maintenance task
Base: main · Commits: 6 · Date: 2026-10-15

Checked: ADR 0002 (module boundaries, read models computed on read, injectable clock), the engineering conventions (page composes, `*.test-support.ts` stand-ins, isolated database, seam catalog), the story's rules and the user decisions of 2026-10-15, glossary/language (`check-language.ts`: no new warnings – the 8 warnings all predate this branch), security, test quality, design, scope. The 9 scenario tests and the maintenance-plan tests pass locally (`vitest --project integration src/app/(team)/team/maintenance`, 14 tests).

What holds up: Maintenance does not import Collection's internals – the page composes `machinesForMaintenance` (Collection) and `dueMaintenance` (Maintenance) as the ST-009 convention says. Due and overdue are computed on read through `today(clock)`, `calendarDate` and `maintenanceDates` (no `new Date()`). Last done = start date or later registration date (HS-20) is in the read model and not in the UI. The restriction goes through the existing `maintenanceTaskAppliesTo`. Retired machines are excluded by Collection's query. Removed tasks are excluded through `maintenancePlan` (see #4). `?task=` is only matched in memory against the due tasks, so a forged ID cannot reach the database or bypass the helpers filter (tested). `requireTeamMember()` guards the page. All output is React-escaped and the museum number in links is `encodeURIComponent`-ed. No command, no migration, no journal entry. "Wartung" sits at G19 row 5 in the line, before "Mehr". The page uses `Page wide` (G16). Overdue is said in words (G6a). The test stand-ins `removeMaintenanceTaskForTest` and `withoutMaintenanceTasks` follow the `retireMachineForTest` / `withoutMachines` precedent, including the guard against the shared database.

Not findings (checked and accepted):
- Machines *Not on display* are listed. The glossary says "never", but the user decided on 2026-10-15 to defer this to ST-056 (status ready). It is documented in the story and in the read model's comment.
- `CMD-TestRemoveMaintenanceTask` / `EVT-TestMaintenanceTaskRemoved` are not in `events.yaml`. They are test stand-ins for ST-041 (ready) in `*.test-support.ts`, the accepted convention.
- The flaky browser tests with 4 workers also happen on `main` and are not caused by this diff.

**Verdict: ready to merge** – 0 blockers, 0 major, 8 minor.
Most important finding: #1/#2 together – ST-056 and ST-041 will both change the inputs of `dueMaintenance`. One published machine shape and one home for "removed tasks are never due" would keep those changes in one place.

## Disposition (`/implement`, 2026-10-15)

- **#1 fixed** – `dueMaintenance` takes Collection's `MachineForMaintenance`; Maintenance declares no second machine type.
- **#2 fixed** – `activeMaintenanceTasks(db)` (module-internal) is the one home of "a removed maintenance task is never due"; RM-MaintenancePlan and RM-DueMaintenance both read it.
- **#3 fixed** – `overdueCount` on a due maintenance task; `machineCount` / `overdueCount` on an entry of the list.
- **#4 skipped** – the glossary lists *Due / Overdue* as one pair, which the catalogue test cannot map to one `terms` key; the words used are the glossary's „fällig“ / „überfällig“. Revisit if a page needs the term as a label of its own.
- **#5 fixed** – an untitled test covers the whole order (most overdue, then most due, then name); removing the tie-breaks fails it.
- **#6 fixed** – `dueMaintenanceAddress` sits next to `dueMaintenanceFilterOf` in `due-maintenance-data.ts`.
- **#7 open** – the filled list cannot be shown in a browser test (every machine there is registered today); the page is one column with `overflow-wrap`. Revisit with ST-044, whose recorded maintenance makes due entries possible in the browser.
- **#8 skipped** – an empty maintenance plan saying „Gerade ist keine Wartung fällig.“ is true; whether technicians get a way to the maintenance plan there is a UX question for the acceptance, not text to decide in code.
