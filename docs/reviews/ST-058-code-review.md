## Checked without findings
- **Module boundaries (ADR 0002):** the page data function composes public queries through each module's `index.ts`: Collection `statusChangesSince`/`machineLabels`/`machinesForMaintenance`, Repair `staleClaims`/`resolvedOrReopenedSince`, Maintenance `dueMaintenance`, Team `teamMemberNames`. Repair refers to machines by ID only, and the page resolves the labels. No schema is imported across modules.
- **Time:** all values are computed on read with the injected clock (`hoursBefore`, `elapsedMoreThanHours`, `formatDateTime` in `time.ts`). There is no `new Date()` in domain code. Overdue maintenance reuses `dueMaintenance`, which applies the rules of ST-043/ST-056 (Not on display excluded).
- **Stale-claim rule:** "more than 336 h" is used, and a work log entry by anyone counts. Work logged before a take-over does not count. Both the exact 336 h edge and the take-over case are covered by the extra test. The claim is never released, and scenario 1 checks this through the `openDefects` read model, not the database.
- **Traceability, language, security:** all 7 scenario titles exist. `check-language.ts` reports no warning in the diff's files. The page is technician-only (ST-048), output is escaped by React, the museum number in the link is URL-encoded, and there are no logs or journal changes.
- **Tests:** every scenario sits at the approved seam (page data function plus `renderToStaticMarkup` in an isolated database), with data set up through commands. The expected values are literals. Scenario 5 deliberately does not arrange the "last visit" Given (user, 2026-10-24). The suite passes (16/16).
- **Changed ST-048 browser test (`e2e/technician-dashboard.spec.ts:41-45`): legitimate.** ST-048's scenario means "the machine no longer waits to return to play". The old assertion (museum number nowhere on the page) was a stand-in that ST-058's specified behaviour (the status change under „Letzte Änderungen“) makes false. The new assertion still checks that section 2's entry ("kein offener Defekt") is gone, and also checks the new section 5 entry. The test checks no less than before.

**Verdict: ready to merge**
Most important finding: #1 – whether a defect on hold can be a stale claim is not decided anywhere. Ask the user instead of letting the code decide implicitly.
