## Remarks (test quality, not acceptance blockers)
- **Test isolation is leaky.** Both integration test files reset `ai_work_hold`, `ai_index_entry` and the AI settings in
  `beforeEach`, but not the `file` table; each test gets a fresh empty `memoryStorage`. Files of earlier tests therefore
  become "waiting" again but fail immediately as `not readable` because their content is gone. The target assertions still
  hold (and scenario 5's "after 2 pages" arithmetic is correct because the leftovers consume no embedding requests), but
  the runs do unrelated work and the result depends on test order. Deleting the files (or resetting the database) in
  `beforeEach` would remove the coupling.
- **Scenario 1 does not exercise `wasmUrl`/`iccUrl`.** The "scan" is an embedded PNG; pdfjs decodes it without the wasm
  decoders or ICC profiles, so this assertion cannot catch their removal. A JBIG2/JPEG-2000 page (or an assertion on the
  asset URLs) would.
- **`items: []` on a failed entry is state-mapper output.** `aiIndexEntryOf` always returns no items for a failed entry,
  so the failure tests cannot detect stray rows in `ai_index_item`; a direct query would be stronger.
- **Re-indexing is untested** (see the invariant row above), and the "cost recorded once" of scenario 10 is inferred from
  one journal event rather than asserted as a value.
