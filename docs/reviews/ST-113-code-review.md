## Checked, no finding
- **`replaces` for attachments, concurrency.** `CMD-RemoveFile` loads without a lock and then saves with `UPDATE … WHERE version = seen`. Under READ COMMITTED, a remove that waits behind a concurrent change (e.g. a future set-delta attach holding the row lock) re-checks the version, gets no row back and reports a conflict. Only after the row update succeeds are the attachments deleted and inserted again, so a removal never writes back a stale attachments list. Re-inserting gets new `position` values but keeps the order, because the entries are loaded by position. Data model *Concurrency* holds.
- **Insert order and foreign keys.** `aggregateStore.insert` writes the file row before `saveLists`, so the `file_attachment.file_id` foreign key is satisfied within the transaction. No code deletes file rows; the store's `remove` is not used for files, so `ON DELETE no action` is right. The four test `beforeEach` blocks now delete `file_attachment` before `file`.
- **Uniqueness.** "To each at most once" is enforced in the decision (`new Set`) and by the unique indexes `(file_id, machine_id)` / `(file_id, machine_model_id)`. NULLs stay distinct, so several model attachments don't collide on machine. The check constraint `file_attachment_one_target` allows exactly one target per row.
- **Dedupe and order.** `filesOfMachineAndModelForAi` orders by title, `addedAt`, position and keeps the first row per file. That row is always an attachment that matches the machine or its model, so the reference check stays right. `filesForAiReferences` keeps the first attachment by position, which matches the copied owner on the AI index entry. `filesOfMachine` / `machineFile` group by `file.id` with `bool_or(model)`, so a file attached to both shows once with „Modell“ (scenario 2).
- **Pending upload bound to `issuedTo` (ADR 0018).** `withUploadedContent` takes the record with a row-level delete on name, `issued_to` and age, so another team member's name gets `content-gone` and leaves the content alone. The scenario 4 test proves this, including that Anna can still add it. The form runner passes `actor.teamMemberId`, and a non-team actor gets `""`, which `isId` refuses. The route still checks the Origin and the session before anything, and removing the owner removes nothing from the 413 / size checks.
- **Forged `machineId` / `machineModelId`.** The Server Action overwrites both with `formData.set` from the page's own record, and `attachedAsChosen` turns `attachTo` into exactly one target. Even if the bound values were tampered with, the command checks that they exist (`isId` first, then a lookup), and any team member may add a file to any machine or model anyway. Nothing is escalated.
- **Authorization.** `addingActors` = helper and technician, as for ACT-TeamMember, checked by the command layer. The page still calls `requireTeamMember`.
- **Migration data.** 0043 copies every file, removed ones included, into one attachment ordered by `attached_at, id`. It fills `added_by` / `added_at` before `SET NOT NULL` and recreates the team member foreign key on `added_by`; that is safe because `attached_by` already had one (0025). 0044 drops the owner foreign keys explicitly; the `file_one_owner` / `pending_upload_one_owner` checks and the `pending_upload` owner foreign keys go with their columns (PostgreSQL drops the constraints that involve a dropped column). It writes no journal entries and makes no AI calls. Both migrations are tested together from `0042_yellow_bushwacker` with production-like data: removed file, retired machine, failed entry, old embedding model, waiting file, pending upload.
- **ADR 0018 / 0015 / 0017.** `makesAiWork` follows EVT-FileAdded and not EVT-FileAttached, and has a unit test for both. Collection still knows nothing of AI, and no query spans two modules' tables.
