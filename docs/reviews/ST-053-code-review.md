# Code review – ST-053: Linking a problem report to a recently resolved defect reopens it
Base: main · Commits: 7 · Date: 2026-10-25

Checked: the diff `main...HEAD`, the context pack, ADR 0002 and 0010, the engineering conventions. `check-language.ts` reports no warning in files of this diff (its 14 warnings were there before). The story's integration tests pass (9 files, 46 tests). Not re-opened, as the user decided them at the test plan checkpoint: `machine-status-without-reopening`, no status choice on ST-052's page, and the „Wegen der Meldung: …“ wording.

What holds: the link, the reopening and the status change are stored in one transaction (`runs`; the test checks the journal order). The 30-day rule uses Berlin calendar days through `platform/time` and the injected clock, and one function (`resolvedRecently`) serves both the offer and the decision. A defect closed on retirement, one resolved more than 30 days ago, and one seen open but resolved meanwhile are rejected in the decision, not only in the UI. The retirement lock order is unchanged (ADR 0010). The reopen reason is stored as text or problem report, never both and never neither, enforced by a check constraint, and the journal keeps no typed text (`project` of EVT-DefectReopened is unchanged). The `resolvedDefects` field holds only IDs and versions the server parses: a forged entry at worst gets a rejection. No visitor page shows reopenings.
