# Code review – ST-002: Take photos with a phone camera and upload them safely
Base: main · Commits: 3 · Date: 2026-09-27

Scope: the kept building block (`src/photo/*`, `next.config.ts`, `vitest.config.ts`, `docker-compose.yml`, `package.json` scripts) against `docs/architecture/photos.md`, ADRs 0001/0002/0006 and the limits in ST-016. The spike page `src/app/spike/photos/*` and the stub login `src/spike/access.ts` were only checked for safe deployment. Deferred items (command layer, journal, message catalogs, CI, team login, rate limits) are not reported.

Checks run: `vitest run src/photo` passes (14 tests). `check-language.ts` shows 1 warning, in pre-existing code (`src/modules/repair/problem-reports.ts`), not in this diff. Behaviour of `acceptPhoto` was checked with a throwaway probe in the scratchpad (no repository files changed):
- A truncated JPEG makes `acceptPhoto` **throw** `VipsJpeg: premature end of JPEG image`.
- A 16000×16000 PNG of 776 KB (256 megapixels) is **accepted**. It is decoded in full: 408 ms and +105 MB RSS per pass.
- A fully transparent PNG is stored **black** (channel means 0/0/0).

Checked and fine:
- The EXIF rotation happens before stripping in both halves, and metadata is stripped: tested with orientation 6 + GPS, and asserted to have no EXIF/ICC/XMP/orientation.
- The limits match ST-016: 20 MB for originals, ≤ 2048 px and ≤ 1 MB stored.
- Photos are stored in the private store under UUID names with `addRandomSuffix: false`.
- Presigned URLs carry the delegation token but are HMAC-signed per pathname, so the `pathname: "*"` token does not let a holder read other blobs.
- `server-only` guards are in place, and the `vitest.config.ts` alias points at the package's own `react-server` empty module.
- The spike page and action check `hasSpikeAccess()` first (`cookies()` makes the page dynamic, so no signed URLs are cached), return no internal data and log nothing.
- `photos.md` matches the code, apart from #5 and #6.

Verdict: ready to merge – there are no blockers, but the 3 majors (#1–#3) should be fixed in this story's refactor step.
Most important finding: #1/#2. `acceptPhoto`, the server check that ST-016 exposes to anonymous visitors, throws on corrupt images instead of rejecting them and puts no pixel bound on decoding, so one crafted ≤ 2 MB file can exhaust the function.
