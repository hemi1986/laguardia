Base: main · Commits: 7 · Date: 2026-09-30

Checked: `git diff main...HEAD`, the context pack (`story-context.ts ST-006`), `docs/domain/events.yaml` (AGG-MachineModel, CMD-CreateMachineModel, HS-10), `docs/architecture/data-model.md`, ADR 0001/0002/0003, `CONTEXT.md`, the engineering conventions and the tdd/codebase-design skills. Ran `npm run verify` (lint, `tsc --noEmit`, 170 unit tests, 63 integration tests against the local PostgreSQL, events/story/traceability/language checks) – all green, `check-language.ts` clean. The Playwright suite was **not** run (needs the dev server and a local technician account).

What holds: `CMD-CreateMachineModel` goes through `aggregateCommand` (load → decide → save → journal) with `creates: true` and `allowedActors: ["technician"]`, so authorization sits in the command layer and the helper case is rejected before the decision runs (ADR 0002, conventions "Writing a command"). The decision is pure – no `new Date()`, no `randomUUID()`, the ID comes from `newId()`. All four rules of the story (title, manufacturer, machine category required; technology fits the category) are enforced in the decision, not in the form; the form's `required` attributes are only a convenience. The invariant table `technologiesPerCategory` matches HS-10 and the data model exactly, including "Other – none". The journal entry carries the aggregate reference plus machine category and technology only – no title, no manufacturer, and the test proves the free text is absent (conventions "The event journal"). `index.ts` exports the command, the read model and types, never the store or the table. The migration is generated and committed, the table has `version` for ST-036. The Server Action only calls `formAction`, `requireTechnician()` runs before the runner, the actor comes from `currentPerson()`, and no field named `actor`/`role`/`teamMemberId` exists. UI texts come from `teamMessages` in the wording of `CONTEXT.md` (Modell, Kategorie – Flipper/Arcade/Sonstiges, Technik), and `NativeSelect` keeps both selects submittable without JavaScript (ST-076), proven by the no-JS browser test.

The change to `e2e/team-shell.spec.ts` is **legitimate, not a weakened test**: the navigation genuinely gained a destination, so the keyboard-order walk gained one `Tab` and one `toBeFocused` assertion, and the per-page loop gained a visibility assertion for "Modelle". The test asserts more than before and still fails if a destination appears twice or in the wrong order.

## What the main session did with these findings (`/implement` ST-006, 2026-09-30)

**Fixed in this story**

- **#1 (major)** – the two table-count assertions are gone. `create-machine-model-command.integration.test.ts` now
  recognises a rejected attempt by a detail unique to the run (`Xenon ${randomUUID()}` as the title, a unique
  manufacturer where the title has to be blank) and asserts that `machineModelsToChooseFrom` holds no such
  machine model. No dependency on what else the run created.
- **#2 (minor)** – the test is renamed to "stores nothing when the machine model is rejected". The journal half of
  the old title was dropped rather than faked: a rejected creating command has no aggregate ID to query
  `journalOf` with, and the alternative (counting entries by type) is the table count of #1 again. That a rejected
  command journals nothing is the command layer's guarantee and is tested at its own seam
  (`src/platform/command/execute-command.integration.test.ts`).
- **#3 (minor)** – the ST-005 browser test is extended and renamed to "a helper cannot reach the technician
  pages": it now also asserts that a helper sees no "Modelle" link and is redirected away from
  `/team/machine-models`.

`node .claude/skills/implement/scripts/verify.ts --e2e` is green after the fixes (170 unit/integration tests,
26 browser tests).

**Raised as open questions instead of decided in the code** (`docs/stories/OPEN_QUESTIONS.md`, 2026-09-30) – all
three are the user's or discovery's call, not an engineering choice:

- **#4** – does the machine model choice deserve an `RM-…` in `events.yaml`, or do the conventions say a query
  internal to one bounded context needs none?
- **#10** – should a year that is not a number be rejected with its own reason instead of silently dropped?
- **#11** – the glossary's composite `_UI (de)_` wording for **Machine category** keeps "Kategorie" out of
  `teamMessages.terms`; split the glossary entry, or loosen the comparison in `messages.test.ts`?

**Skipped minors, with the reason**

- **#5, #6, #7** – all three are "correct as it stands, revisit when the second caller arrives" (ST-007 for the
  read model's own return type, ST-036 for writing the event's fields out and for moving the aggregate's
  vocabulary out of the create command's file). Changing them now would be design on speculation.
- **#8** – the shared `commandErrors["not-authorized"]` wording is technician-specific. True, but every command
  that reaches this catalogue today is technician-only; the first team command a helper may also run (ST-009,
  ST-012) is where the neutral wording belongs, together with a case that proves it.
- **#9** – the duplicated `logIn` helper across four browser specs. Real duplication, no behaviour at risk;
  whichever browser-test story comes next (ST-068) can move it into `e2e/fixtures.ts`.

None of the eleven findings clears the follow-up hurdle, so **no follow-up story was created**.
