Security pass: the action calls `requireTechnician()` before the runner, and authorization proper is `allowedActors: ["technician"]`. The acting person comes only from `currentPerson()`. CSRF is covered by the proxy and the Next.js Origin check for Server Actions. `index` and `version` go through `wholeNumber`/`versionSeen`. Anything that is not an integer becomes `-1` and is refused by the decision. An out-of-range or negative index reads `undefined` and is refused. Nothing posted reaches the store except the proposal ID, which is handled like in „Verwerfen“. The journal entry holds only `documentIndex`, with no title or address. I found no injection, data-leak or privilege issue. The only security-relevant defect is the integrity problem in #1: a technician's tap can retry a different link than the one shown.

Verdict: **fix blockers first**
Most important: #1. The page posts each link's position among the *chosen* documents, but the command reads the position among *all* written documents. As soon as one proposed document was left unticked, „Nochmal versuchen“ is either rejected or retries the wrong link.
