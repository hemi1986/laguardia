# 0015 – AI work runs in the background: found from the database, started after the response, continued by itself; what breaks off fails

Supersedes, once accepted and for AI assistance only, one point of `docs/adr/0002-modular-monolith-state-based-persistence.md` (accepted, not edited): "no background workers". ADR 0002's "no scheduler or cron job" stays in force – AI work has no scheduled job either (user, 2026-11-01, decision D3 in `docs/reviews/2026-11-01-story-review.md`). Everything else in ADR 0002 holds – the automatic policies of Collection, Repair and Maintenance stay synchronous, and *due*, *overdue* and the other time-based events stay computed on read. ADR 0009's cleanup of abandoned uploads is unchanged.

## Context and Problem
Feature `ai-assessment` brings the first work that cannot run inside a request: writing an AI assessment takes up to a few minutes (a chat completion with photos and page images), indexing a scanned 100 MB manual takes minutes, and turning AI on or changing the embedding model indexes every file of every machine and machine model – far longer than one function may run. The user decided: AI assessments and indexing run in the background, and the defect page refreshes itself while an AI assessment is being written (`docs/domain/events.yaml`: `POL-RequestedAiAssessmentIsWritten`, `POL-AttachedFileIsIndexedForAi`, `POL-AiIndexFollowsTheSettings`, `RM-DefectAiAssessments`; user, 2026-10-31). Nothing is retried automatically: work that fails or breaks off is shown as failed and tried again only by hand (`POL-UnfinishedAiWorkFails`, `EVT-AiWorkLeftUnfinished`; user, 2026-11-01, D3). ADR 0002 has no background work, and expected an outbox "if a policy ever needs to become asynchronous".

## Driving Requirements
- The team member does not wait on the page; the AI assessment shows "being written", then written or failed – `POL-RequestedAiAssessmentIsWritten`, `RM-DefectAiAssessments`
- Files are indexed in the background on attach and all of them when AI is turned on or the embedding model changes – `POL-AttachedFileIsIndexedForAi`, `POL-AiIndexFollowsTheSettings`
- **No cron job and no automatic retry** (user, 2026-11-01, D3). A failed piece of work stays failed until someone taps „Erneut versuchen“ (or removes the file). A piece of work that ends without a result – a crash, a deployment, the time limit – fails as *broken off* and is never taken again by itself, so it never costs twice on its own – `POL-UnfinishedAiWorkFails`, `EVT-AiWorkLeftUnfinished`, resolved HS-32 and HS-33
- **The design targets a runtime without a short time limit.** The user will not buy Pro and plans to run La Guardia later in a self-hosted Docker installation instead of Vercel and Neon; the design does not work around the Vercel Hobby time limit (user, 2026-11-01, D1). **The project is on Vercel Hobby for now** (spike ST-105, 2026-11-01): a function runs **300 s at most**; a deployment with a longer `maxDuration` is refused. For comparison, Vercel Pro in `fra1` (ADR 0006): a function runs 300 s by default and at most 800 s (1800 s in beta); 2 GB memory by default, 4 GB at most; `after()` work counts against the function's duration – https://vercel.com/docs/functions/limitations
- Minimal operating effort, one volunteer – `docs/product/vision.md`; the database scales to zero when idle (Neon, ADR 0006 cost estimate)
- The whole application runs locally in Docker without a cloud account – `docs/adr/0012-s3-compatible-object-storage.md`; testing during implementation is local (user, 2026-11-01, D2)
- The state of every AI assessment and AI index entry is domain state that read models show – `docs/architecture/data-model.md`

## Considered Options
1. **Run the work inside the request** – rejected: the team member would wait minutes, and indexing everything does not fit any function's time limit.
2. **State in the database, a run started after the response (`after()`) and continued by itself when its time is up; work that breaks off fails** – chosen.
3. **Vercel Workflow** (durable steps, retries, no duration limit) – rejected: the work's state would live twice – in Workflow's own store and in the domain tables the pages read –, it adds a compiler plugin, directives and a local "world" to the build and the tests, and it is a Vercel-only product right after ADR 0012 removed one for local parity; the user expects to leave Vercel.
4. **Vercel Queues** – rejected: the same second place for state, at-least-once delivery to handle anyway, a consumer function per topic and no local equivalent in the Docker setup.
5. **A frequent cron (every few minutes) as the only trigger** – rejected: it would wake the database all day and end its scale-to-zero, and an AI assessment would wait for the next tick.
6. **A daily cron as a safety net** that takes again what a crash, a deployment or a broken chain left and retries files that failed at OpenRouter – rejected by the user (2026-11-01, D3): a piece of work that does not fit one run (a too-large PDF on Hobby) would be paid for again every night, a cron runs only for production on Vercel and needs its own secret, and the failures it would cover are rare enough to retry by hand. Without it, ADR 0002's "no scheduler or cron job" holds.
7. **An outbox table** (ADR 0002's anticipated way) – not needed: the stored state already says what is left to do – AI assessments still *requested*, and files without an AI index entry for the current embedding model (*waiting*, derived) – so nothing extra is written in the triggering transaction and Collection's commands stay unaware of AI.

## Decision
- **The work is found, not sent.** A run of the AI work asks the database what is left: first it fails what broke off (below), then it takes AI assessments still requested (a person is waiting), then waiting files while AI is on. Failed files are never taken (HS-32). No message, no outbox, no data handed over from the triggering command.
- **One worker route** in the app (`/api/ai-work`, a route handler) does every run, configured on Vercel with the plan's longest `maxDuration` – on Hobby the literal `300`, since a deployment with more fails; the default memory is enough (ST-105: ≈ 320 MB for the largest manual). It accepts only requests carrying the deployment's worker secret (an environment variable of its own), answers at once and does the run in its own `after()`. Requests from pages never run AI work in their own function.
- **Started after the response – the only triggers.** The Server Actions that make work – saving the AI settings, requesting an AI assessment, attaching a file, „Erneut versuchen“ – call the worker route in `after()` once their command has committed (a short request; the page does not wait for it). Per HS-33, the defect page, refreshing itself while an AI assessment is being written, does the same once that AI assessment's hold has run out. Whatever started it, a run takes all work that is left – so waiting work a broken chain of runs left behind is taken by the next run any of these starts. There is no scheduled run.
- **A piece of work is one AI assessment or one whole file.** A run indexes a whole file or nothing: there is no progress kept across runs, and a file whose indexing is cut off stores nothing.
- **A run holds what it works on.** It takes one piece of work at a time and holds it for a limited time in a short transaction (`FOR UPDATE SKIP LOCKED` on a small technical hold record – file or AI assessment, held until; not domain state, `docs/architecture/data-model.md`), so several runs share the work instead of doing – and paying for – it twice. The slow part runs outside any transaction; the result is stored through the aggregate's command in one short transaction with its usual checks (still requested; file not removed, under the file's removal lock of ADR 0014), and that transaction ends the hold. A run that gives a piece up on purpose (AI turned off) ends its hold without a result.
- **The budget is a setting, and a hold outlasts it.** A run's budget is how long it may work; a piece of work is expected to fit within one budget (a self-hosted server sets it far above the longest indexing; on Hobby it is about 250 of the 300 seconds). A hold lasts longer than the budget and is derived from it, so it outlives every piece that fits, and no hold is ever renewed.
- **What breaks off fails, once.** A hold that ran out without a result means the piece was cut off – a crash, a deployment, the time limit (`EVT-AiWorkLeftUnfinished` is this derivation, not a record). Such a hold is never taken again: the next run, whatever started it, records the piece failed with reason *broken off* through the aggregate's command and drops the hold in the same transaction (`POL-UnfinishedAiWorkFails`). It is tried again only by hand – „Erneut versuchen“ on the file or a new request for the defect.
- **Continued by itself.** A run stops taking new work once its budget is used, and if work is left it calls the worker route again before it ends. Turning AI on with a few hundred files is therefore a chain of runs within minutes to an hour. If a self-call fails, the chain stops; what was not yet taken stays waiting for the next trigger.
- **Tests** drive one run directly through its function with the injected clock, database, AI seam (ADR 0014) and storage seam; the call of the worker route is an injected function. No test waits for a real background run.
- **One item per embedding request, a few requests in parallel** (ST-105): OpenRouter routes a request with several inputs to an endpoint without zero data retention, which the provider rule refuses.

## Consequences
- Positive: no new service, store, product or scheduled job; the pages read the same tables the work writes; local development and CI run the same code; the database wakes only when someone makes work. A piece of work never costs twice unless someone asks for it.
- Negative / cost:
  - **Accepted limitation on Vercel Hobby** (user, 2026-11-01, D1): a PDF that does not fit one run does not finish there. Measured by ST-105: 0,89 s per page on Vercel, so a run of 250 s indexes ≈ 280 pages; the largest manual has 568 pages and needs ≈ 505 s. Such a PDF is cut off with its run and stores nothing; once its hold has run out, the next run records it failed as *broken off* (D3). It costs the embeddings of the pages it reached once (≈ 0,00019 $ per page) and again only for each „Erneut versuchen“. It is documented, not designed around – on a self-hosted server with a budget above the longest indexing it finishes.
  - Indexing all files after turning AI on is a chain of runs on Hobby – as intended.
  - A failure at OpenRouter (not reachable, refused) is not retried by itself; a technician sees the file failed in the AI index overview and taps „Erneut versuchen“ (HS-32, D3).
  - A run in progress during a deployment is cut off; the pieces it held fail as *broken off* and need „Erneut versuchen“ (HS-33 for AI assessments).
  - The self-call can fail (a deployment in between); a broken chain waits for the next trigger – an attached file, a request, saving the AI settings or „Erneut versuchen“. With nothing triggering, waiting files stay waiting.
  - Until a run notices a file whose indexing broke off, the file still counts as waiting; opening the form „KI“ starts that run (HS-35).
  - A new secret per environment: the worker secret; `docs/operations/` gets the steps.
  - Previews are not a place to try AI work (D2): while Vercel's deployment protection is on for previews it refuses the call to the worker route there, and no bypass secret is configured.
- Follow-up: the engineering conventions get a section *Background work* after the first story that builds it (the worker route, holds, budget, continuation, broken-off work, how a story tests a run).

## Open Points
- HS-35 (resolved, user 2026-11-01): opening the form „KI“ starts a run when a hold has run out, like the defect page does for AI assessments.
- HS-32 and HS-33 are resolved (user, 2026-10-31, changed by D3 on 2026-11-01): no automatic retry of failed files; a hold lasts longer than the budget and is derived from it, and an AI assessment whose hold ran out without a result fails as *broken off* and is not written again.
