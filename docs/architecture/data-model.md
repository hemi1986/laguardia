# Logical Data Model

> Stack-neutral. Source: `docs/domain/events.yaml`. Glossary: `CONTEXT.md`. Contexts: `docs/domain/context-map.md`. As of: 2026-10-25 (per-machine maintenance)
>
> No physical model yet – the stack is only *proposed* (`docs/adr/0001-tech-stack.md`, `0002`, `0003`). A "Physical Model" section follows once the user accepts them.

## Conventions

- **References across aggregates are IDs only** (`MachineId`, `DefectId`, `TeamMemberId`, …). Within an aggregate, entities and value objects belong to their root.
- **Time of change**: every event has an occurrence time. Attributes named `… at` whose event lists no explicit time (e.g. `Claimed at` from `EVT-DefectClaimed`) take the occurrence time of that event. Where the event names a time explicitly (`Reported at`, `Logged at`, `Recorded at`), that is the source.
- **Derived, not stored**: *Due*, *Overdue*, *Last done*, *Due since*, counts and "waiting longer than 3 days" / "claims older than 14 days" are computed from stored data when read (`EVT-MaintenanceTaskDue` and `EVT-MaintenanceTaskOverdue` have `origin: time` and no aggregate).
- **People**: every "… by" is a `TeamMemberId` from the Team area (not modelled, see the end of this document). The only anonymous actor is the visitor as reporter of a problem report.

## Problem report (`AGG-ProblemReport`, context `BC-Repair`)

**Invariants**
- A problem report refers to exactly one machine, which never changes
- A problem report is triaged at most once – exactly one outcome (defect recorded, linked, resolved on the spot, dismissed)
- Once triaged, the outcome of a problem report never changes
- A problem report with the outcome defect recorded or linked refers to exactly one defect of the same machine
- A problem report dismissed as spam has no description and no photo

**Concurrency (HS-16):** the problem report is the consistency boundary of triage. *Record defect* is handled by the problem report, which marks itself triaged and creates the defect in one step; a concurrent second triage fails the version check on the problem report and is rejected.

**Reported and triaged in one step (CMD-ReportProblem, user 2026-10-10):** a technician's problem report – and a helper's that is resolved on the spot – is stored already triaged: EVT-ProblemReported and the triage event (plus, for *defect recorded*, the new defect and an optional machine status change) are stored together or not at all. *Untriaged* is then never a stored state of that problem report; no new attribute is needed.

**Lifecycle**

```mermaid
stateDiagram-v2
    [*] --> Untriaged : EVT-ProblemReported
    Untriaged --> DefectRecorded : EVT-DefectRecorded
    Untriaged --> Linked : EVT-ProblemReportLinkedToDefect
    Untriaged --> ResolvedOnTheSpot : EVT-ProblemResolvedOnTheSpot
    Untriaged --> Dismissed : EVT-ProblemReportDismissed
    DefectRecorded --> [*]
    Linked --> [*]
    ResolvedOnTheSpot --> [*]
    Dismissed --> [*]
```

## Defect (`AGG-Defect`, context `BC-Repair`)

**Invariants**
- A defect refers to exactly one machine and to the problem report it was recorded from; neither ever changes
- A defect is either open (possibly on hold), resolved, or closed on retirement
- A resolved defect can only be reopened – no claiming, prioritizing, hold, change of its details, work log entry, resolving again or closing on retirement
- A defect closed on retirement is final – it cannot be reopened or changed
- A defect has at most one claimant
- Only defects suitable for helpers can be claimed by, assigned to or resolved by helpers
- Only an open defect that is not on hold can be put on hold; only a defect on hold can be resumed
- Resolving and closing on retirement end the claim and any hold; a reopened defect is open, not on hold and unclaimed
- Work log entries are only added, never changed or removed

**Lifecycle** – prioritizing, claiming, releasing and logging work happen inside *Open* and do not change the state.

```mermaid
stateDiagram-v2
    [*] --> Open : EVT-DefectRecorded
    state Open {
        [*] --> InProgress
        InProgress --> OnHold : EVT-DefectPutOnHold
        OnHold --> InProgress : EVT-DefectResumed
    }
    Open --> Resolved : EVT-DefectResolved
    Resolved --> Open : EVT-DefectReopened
    Open --> ClosedOnRetirement : EVT-DefectClosedOnRetirement
    ClosedOnRetirement --> [*]
```

`InProgress` is only the name of the "open and not on hold" sub-state in this diagram, not a domain term.

Whom a claim was taken over from is data of `EVT-DefectClaimed` only, kept in the event journal as a `TeamMemberId` reference – not an attribute of the *Claim* value object; the confirmation after taking over reads it there (ST-025). Likewise journal-only: the *Former claimant* of `EVT-DefectClaimReleased`, and which details changed in `EVT-DefectDetailsChanged` (title, suitable for helpers or both) together with whose claim that change released in the same step (*Released claim of*, a `TeamMemberId` reference – the confirmation after the change reads it there, ST-031) – none is an attribute of the defect (story review 2026-10-17).

A defect keeps one *Resolution* per resolve and one *Reopening* per reopen; both are only added, never changed. In the order they happened they alternate, so the repair history (`RM-MachineRecord`) shows each closing note with the reopen reason that followed it. Derived: *Last work log entry* (`RM-OpenDefects`), time to first work log entry and to resolved (`RM-RepairTimes` – after a reopen the latest resolution counts, decided in ST-051).

## Machine (`AGG-Machine`, context `BC-Collection`)

**Invariants**
- A machine refers to exactly one machine model
- A machine always has exactly one museum number
- A machine always has exactly one machine status
- Every machine status change is kept in the machine's status history with previous status, new status, reason and who changed it
- A retired machine is final – it stays retired and cannot change status, be moved, have its details corrected or be retired again
- Helpers can only set Out of order

**Set-based rule (HS-17):** the museum number is unique among all machines, retired ones included – checked by *Register machine* and guaranteed atomically by the machine store, not by a single machine.

**Lifecycle** – inside *Registered*, `EVT-MachineStatusChanged` can move between any two machine statuses; the initial status comes from `EVT-MachineRegistered`.

```mermaid
        via EVT-MachineStatusChanged

    Registered --> Retired : EVT-MachineRetired
    Retired --> [*]
```

## Machine model (`AGG-MachineModel`, context `BC-Collection`)

**Invariants**
- A machine model always has a title, a manufacturer and exactly one machine category
- The technology fits the machine category (Pinball – EM, Solid-state, DMD, LCD; Arcade – CRT, LCD; Other – none)
- A machine model has either no year or a four-digit calendar year (deliberately no plausibility range – 1067 and 2999 are allowed)

**Lifecycle**

The **category history** is append-only, like the machine status history: its first entry holds the machine category and technology given at creation, and every correction that changes either appends one with the correction's point in time (ST-036, user 2026-10-18). A correction of title, manufacturer or year appends nothing. Machine models created before ST-036 got their first entry from the journal's EVT-MachineModelCreated. Collection published it for Maintenance to know since when a restricted maintenance task applied to a machine; since FLOW-PerMachineMaintenance (2026-10-25) maintenance tasks apply to chosen machines and Maintenance reads only the **current** machine category and technology, for grouping and proposing machines. The history's last reader is the one-off migration of HS-23/HS-24 (the date each machine started counting); after it, the category history has no reader and is kept anyway (user, 2026-10-25, HS-24).

## Maintenance plan (`AGG-MaintenancePlan`, context `BC-Maintenance`)

**Invariants**
- Every maintenance task has a positive interval
- A maintenance task applies to any number of machines – none included – and to each machine at most once
- A removed maintenance task is final – its instruction, interval, suitable-for-helpers mark and machines never change, it never becomes due again, and its maintenance records are kept

**Machines of a maintenance task (FLOW-PerMachineMaintenance, user 2026-10-25):** each task holds the machines a technician chose for it, by `MachineId`, each with the moment it was added. There is no restriction to machine category or technology and no start date any more; category and technology only group and propose machines in the choice read models (`RM-MachineChoiceForMaintenanceTask`, `RM-MaintenanceTaskChoiceForMachine`). Removing a machine ends its entry (it is marked with *Removed at*, never deleted) – the journal (`EVT-MachinesOfMaintenanceTaskChanged`) keeps who removed it and when; its maintenance records stay. Adding it again starts the same entry anew with a new *Added at* and no *Removed at* (ST-095). A retired machine's entry may stay; it never counts (see *Derived* below), so no policy reacts to `EVT-MachineRetired` in Maintenance and a machine retired while it is being added needs no retirement lock. Registering a machine with chosen maintenance tasks adds it to each of them in the registration's transaction (`POL-RegistrationAppliesChosenMaintenanceTasks`, HS-22).

**Lifecycle** of a maintenance task within the plan (`EVT-MaintenancePlanChanged` covers added, changed and removed; `EVT-MachinesOfMaintenanceTaskChanged` changes its machines and leaves its state alone):

```mermaid
stateDiagram-v2
    [*] --> Active : EVT-MaintenancePlanChanged (added)
    Active --> Active : EVT-MaintenancePlanChanged (changed)
    Active --> Active : EVT-MachinesOfMaintenanceTaskChanged
    Active --> Removed : EVT-MaintenancePlanChanged (removed)
    Removed --> [*]
```

A new task and its first machines are stored together (`CMD-ChangeMaintenancePlan` produces both events).

| Maintenance plan | Root | – | – | – | singleton, one per museum |
| Maintenance task | Entity | ID | `MaintenanceTaskId` | yes | – (identity) |
| | | Name | `Title` | yes | EVT-MaintenancePlanChanged ("Maintenance task") |
| | | Instruction | `Text` | yes | EVT-MaintenancePlanChanged |

| | | Added at | `Timestamp` | yes | EVT-MachinesOfMaintenanceTaskChanged (occurrence of the event that added it; for migrated tasks see HS-23/HS-24) |

### Derived: due status per machine and maintenance task (not stored)

A maintenance task **applies** to a machine when the task is not removed, the machine is one of the machines of the task and the machine is not retired. Machine category, technology and machine model corrections play no part (FLOW-PerMachineMaintenance, user 2026-10-25). For each applicable pair:

- *Last done* = latest *Date (carried out)* of a maintenance record with outcome *done* for that machine and task, counting only records recorded since the machine's *Added at* – a record backdated to before the day it was added still counts if it was recorded afterwards; one from before a removal does not (HS-24, user 2026-10-25). Without such a record there is no *Last done* (`RM-DueMaintenance` shows none).
- *Due since* = *Last done* + *Interval*; without a *Last done*, the day of *Added at* – the task is due at once on a machine it newly applies to, also on one added again after a removal. Calendar days in Europe/Berlin.
- Never due while the machine is *Not on display* (status history). A machine returning from *Not on display* follows the normal rule; only a task already due at the return counts as due since the return date, overdue counted from there (HS-20). This covers a machine that was *Not on display* when it was added: the task becomes due on its return.
- *Overdue* once due for more than 25% of the interval.
- Superseded (2026-10-25): the task's start date, the machine's registration date as a floor for *Last done*, and the rule that a task newly applying after a machine model correction counts as last done on the correction date (ST-044, HS-20 D5, ST-036).

```mermaid
    [*] --> Suspended : EVT-MachinesOfMaintenanceTaskChanged (added, Not on display)
    NotDue --> Due : EVT-MaintenanceTaskDue
    Due --> Overdue : EVT-MaintenanceTaskOverdue
    Due --> NotDue : EVT-MaintenanceRecorded (done)
    Overdue --> NotDue : EVT-MaintenanceRecorded (done)
    NotDue --> Suspended : EVT-MachineStatusChanged (Not on display)

    Due --> [*] : EVT-MachinesOfMaintenanceTaskChanged (removed) / EVT-MachineRetired / task removed
    Overdue --> [*] : EVT-MachinesOfMaintenanceTaskChanged (removed) / EVT-MachineRetired / task removed
    Suspended --> [*] : EVT-MachinesOfMaintenanceTaskChanged (removed) / EVT-MachineRetired / task removed
```

`Suspended` is only a diagram label for "machine not on display", not a domain term. The state starts when the machine is added to the task and ends when it no longer applies.

## Team member (Team area – generic, not modelled)

Not an aggregate of this model; listed only because all contexts reference it (`docs/domain/context-map.md`, `docs/adr/0004-team-authentication.md`).

| Attribute | Domain type | Required | Source (event/read model) |
|---|---|---|---|
| ID | `TeamMemberId` | yes | every "… by" in events |
| Name | `Text` | yes | *Claimed by*, *Reporter* in RM-OpenDefects, RM-TriageList |
| Role | *Helper* \| *Technician* | yes | command rules (e.g. CMD-ClaimDefect, CMD-ChangeMachineStatus) |
| Current dashboard visit began at | `Timestamp` | no | beginning of the team member's current *dashboard visit*; set on the first visit and whenever a new dashboard visit begins (more than one hour after this value) – ST-050, `docs/adr/0011-recording-the-last-visit.md` |
| Last visit | `Timestamp` | no | *New since last visit* in RM-TechnicianDashboard, RM-HelperDashboard – where the previous dashboard visit began; on the first visit the first visit's own beginning (HS-21, ST-050, ADR 0011) |

Both visit values are absent until the team member's first dashboard visit, are one pair per team member shared across all devices, and are owned and written only by the Team area. They are per-member state, **not journaled**: opening the dashboard appends no event (ADR 0011). One rule derives both from the stored pair and the moment of opening (story review 2026-10-17, decision 2):

| Situation when the dashboard is opened | Current dashboard visit began at | Last visit |
|---|---|---|
| never visited | the opening | the opening (nothing is marked) |
| at most one hour after the current visit's beginning | unchanged | unchanged |
| more than one hour after the current visit's beginning | the opening | the previous *Current dashboard visit began at* |

The dashboards compute their mark line with this rule at display time and never write it.
