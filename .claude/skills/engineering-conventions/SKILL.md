# Engineering Conventions

Written from the code as it stands after ST-003 (2026-09-27). The ADRs decide *what*; this file says *how* it is done here. When the code and this file disagree, raise it – don't silently follow either.

## Module layout

```
src/
  app/              Next.js pages and Server Actions – thin: parse the form, call a command or a read model, render
    _actions/       the Server Action runner (ST-073): `formAction`, `currentPerson()` – a private folder, not a route
  modules/
    collection/     BC-Collection – machines, machine models, files
    repair/         BC-Repair – problem reports, defects
    maintenance/    BC-Maintenance – maintenance plan, maintenance records
    team/           BC-Team – team members, roles
  components/       shared UI (ST-076): `page.tsx` (the 360 px page container), `ui/` the shadcn components
  lib/              `cn` re-export, the alias shadcn's components import
  platform/         shared kernel: command layer, event journal, clock, time convention, database, message catalogs,
                    storage seam (`storage/`, ST-016)
  photo/            photo module (ST-002, ST-016): `index.ts` (server) and `browser.ts` (client) are its public interface
  upload/           direct uploads from the browser (ST-085, ADR 0009): pending uploads, attaching, cleanup – `index.ts`
                    (server) and `browser.ts` (client) are its public interface
  test-support/     test data builders, test database – only for tests (ST-067 enforces it)
  proxy.ts          CSRF check for every POST to a page; renews the session cookie on every page request
scripts/            one-off command-line scripts (e.g. `npm run setup:first-technician`), run with tsx
e2e/                browser tests (Playwright, 360 px)
drizzle/            migrations (generated by `npm run db:generate`, run in the Vercel build)
```

Inside a module (flat until it grows):

| File | Contains |
|---|---|
| `index.ts` | the module's **public interface** – the only file other modules and `src/app/` may import |
| `schema.ts` | Drizzle tables of the module's aggregates (collected by `drizzle.config.ts`) |
| `<command>.ts` | the pure **decision** of a command and the aggregate's state/event types (e.g. `report-problem.ts`) |
| `<command>-command.ts` | the command definition, `aggregateCommand({ … })` (e.g. `report-problem-command.ts`) |
| `<aggregate>s.ts` | the aggregate's store (`aggregateStore`, row ↔ state) and its read-model queries (e.g. `problem-reports.ts`) |
| `*.test-support.ts` | test stand-ins of a module, imported only by its tests |
| `*.test.ts` / `*.integration.test.ts` | next to the code they test |

**Import rules** (lint, `eslint.config.mjs`, ADR 0002):
- A module is used only through its `index.ts`. Inside a module, import freely. **One exception, for tests only**
  (user, 2026-10-02, ST-009): a `*.test.ts` may import another module's `*.test-support.ts` – its stand-ins for
  commands that don't exist yet –, e.g. a page test that needs a machine with a changed status before ST-012.
- Direction: `app` → `modules` → `platform`. The platform imports no module or page code (its tests may drive a module command); a module imports no page code.
- A module's `index.ts` exports commands and read-model queries – **never** its persistence functions or tables. Other modules change its data only through its commands.

## Shared UI components (ST-076)

shadcn/ui on Tailwind v4 (`components.json`, ADR 0001). The components are **owned in the repository** – they are
copied in, not a dependency that is upgraded – so a copied file may be edited like any other source file.

- **Where:** `src/components/ui/<component>.tsx`; the page container with the phone rules is
  `src/components/page.tsx`. The `cn` helper lives at `src/lib/utils.ts` (shadcn's alias target); the copied
  components import it straight from the `cn` package.
- **A component carries no domain logic and no texts.** It receives its texts as props – the message catalogs
  stay in the pages. `eslint.config.mjs` enforces it with the `ui` boundary element and its own disallow policy
  (a component may not import a module, the platform or the app); `src/platform/module-boundaries.test.ts`
  proves it with a deliberate violation. The element needs its **own** policy – being listed as an element is
  not enough, because `default: "allow"` lets anything through that no policy names.
- **Adding one:** `npx shadcn@latest add <name>`, then read the copied file before committing it – it lands in
  the repository and is ours from then on.
- **Deviation from ADR 0001, recorded in ST-076:** the ADR expects copied components to mean "no UI library
  upgrades". This shadcn version only copies the wrappers – they import `@base-ui/react` at runtime, and
  `globals.css` imports `shadcn/tailwind.css`. So there *are* two UI packages to keep an eye on; what the ADR
  buys is that the markup and the classes are ours to change.
- **The 360 px rules live in `Page`** (single column, padding, maximum width, word wrapping). A page sets no
  padding, width or column layout of its own. A list page passes `wide` (about 672 px, UX guideline G16 – O2
  settled in ST-008); a form page does not. The team navigation uses the wide width, so it lines up with every page.
- **The team navigation** (`src/app/(team)/navigation.tsx`) follows the table under UX guideline G19: a new
  destination goes to its decided place – the line or "Mehr" –, never somewhere a story picks. Browser tests open
  "Mehr" with `openMore(page)` from `e2e/fixtures.ts` before they click or miss a managing destination.
- **Select: use the native `NativeSelect`, not shadcn's `select`.** shadcn's select (Base UI) renders a
  `<button>` trigger and a JavaScript-driven listbox with no native form control, so with JavaScript disabled no
  value can be chosen or submitted – checked on the copied component in ST-076, which is why it was removed
  again. Every field that must submit without JavaScript uses `NativeSelect`; a scripted component is only an
  option where the interaction needs JavaScript anyway. `e2e/no-js-form.spec.ts` guards it.

### The shadcn skill, and where it does not apply here (2026-10-01)

`.claude/skills/shadcn/` is the official shadcn skill, installed so that component work stops being guesswork
(APIs, composition, `--diff` updates, the Tailwind rules – `gap-*` over `space-y-*`, `size-*`, semantic tokens,
`cn()`). It triggers by itself whenever `components.json` is in play, and its tools are limited to the shadcn CLI.
It knows shadcn; it does **not** know the four decisions below, and it will cheerfully argue against each one.

**The no-JavaScript test – the one that matters.** A copied component becomes a form field only if, with
JavaScript switched off, (a) a value can be chosen and (b) that value arrives in the submitted form data. The
reason is not purity: a Base UI control renders a `<button>` plus `role="listbox"` divs and keeps the value in
React, so there is no form control in the DOM at all – nothing to pick, nothing to submit. Checked on the copied
file in ST-076, which is why shadcn's `select` was removed again and `NativeSelect` exists; `e2e/no-js-form.spec.ts`
guards it. It is a test, not a blacklist: `Checkbox`, `Switch` and `RadioGroup` often *do* render a hidden native
input and pass. Record the outcome here when you test one, so nobody tests it twice. Tested so far: `NativeSelect` passes (ST-076);
`textarea` passes – it is a styled native `<textarea>` (ST-013, `e2e/report-problem.spec.ts` without JavaScript).
`Input` with `type="date"` and `type="number"` passes – a styled native `<input>`, the browser sends `YYYY-MM-DD` and the
digits (ST-040, `e2e/maintenance-plan.spec.ts` without JavaScript).
The skill's "Form inputs: `Input`, `Select`, `Combobox`, …" table has not run this test. A scripted component is
still fine where the interaction needs JavaScript anyway (the camera photo, ST-002/ST-016).

**The form layout moves to shadcn's `Field`** (user, 2026-10-01). Our hand-rolled `src/components/ui/field.tsx`
(38 lines: label wraps control, `aria-describedby` for the description) is replaced by shadcn's `field` with its
`label` and `separator` dependencies – for `data-invalid` on the field, `aria-invalid` on the control and a
`FieldError` with `role="alert"`, which is what UX guidelines G8/G9 need. shadcn's Field supports `NativeSelect`
explicitly, so this costs us none of the no-JavaScript guarantee.
Until the migration is finished **both patterns exist, and that is the one thing to avoid spreading**: the first
form on the new pattern is ST-007 (`src/app/(team)/team/machines/new/register-machine-form.tsx` – `Field` with
`data-invalid`, `FieldLabel htmlFor`, the control with `aria-invalid` and `aria-describedby` pointing at the
rejection, `FieldDescription` for a hint). Of the four forms that predate it, the login and the own-password page were
moved directly (backlog grooming 2026-10-11), the machine models form with ST-036 (`MachineModelFields`, shared by
creating and correcting – `src/app/(team)/team/machine-models/machine-model-fields.tsx`); the team members page
follows with ST-081. The hand-rolled field is renamed `LabelledField` (`src/components/ui/labelled-field.tsx`) until
then. Write no new form on `LabelledField`. Put a field's `key` before a spread of its props – after a spread, React's
JSX transform falls back to `createElement` and warns about the select's option list (ST-036).
**A form whose action is not a command** (the login – `logIn` of the Team module, backed by Better Auth) cannot use
`formAction`; its Server Action mirrors the contract by hand: `(previous, formData) => { error, values } | null`, used
with `useActionState`, and `values` never holds a password (`src/app/login/actions.ts`, `log-in-form.tsx`).

**A new component is a decision, not a convenience.** "Callouts use `Alert`", "Empty states use `Empty`", "Use
`Badge`", "Use `Skeleton`", "use `toast`" are each a new file to maintain and a second UI package in the bundle.
Adding one happens in a story, with a reason – `Confirmation`/`Rejection` in `src/components/ui/message.tsx`
already cover what `Alert` and `toast` would. Decided so far: `field`, `label` and `separator` came in with ST-007
(see above), and `lucide-react` is the icon library `components.json` already names: `Confirmation` carries a tick,
`Rejection` a warning symbol, both `aria-hidden` (UX guideline G9, user 2026-10-01).

**Never run `apply` or `init --preset`.** Both rewrite the theme, the CSS variables and installed components across
the whole application. The style (`base-nova`, `components.json`) was decided in ST-076; changing it is an ADR-level
decision for the user, never a step in a story.

## Domain language and IDs

- Names come from `CONTEXT.md`, never an _Avoid_ synonym. A new term goes into `CONTEXT.md` first.
- Commands, events, aggregates, read models and policies carry their ID from `docs/domain/events.yaml`: `id: "CMD-ReportProblem"`, `type: "EVT-ProblemReported"`, `AGG-ProblemReport`. `verify.ts` checks it.
- Opaque IDs (`MachineId`, `DefectId`, …) are UUIDs from the **injected** ID generator (`context.newId()`), never `randomUUID()` inside a command.
- Enumerations are lowercase kebab-case strings: `"out-of-order"`, `"team-member"`, `"description-required"`.

## Writing a command

Every command has one shape (ST-071, architecture review 2026-09-27, Q2/Q11/Q12/Q14): **load → pure decision → save → journal**. `aggregateCommand` (`src/platform/command/aggregate.ts`) is the only public way to write one; the layer does the loading, saving, version check and journaling.

```ts
// problem-reports.ts – how the aggregate is stored; the version lives only in the store
export const problemReports = aggregateStore({ type: "AGG-ProblemReport", table: problemReport, toState, toRow });

// report-problem.ts – the pure decision: (state, input, { actor, clock, newId }) → new state + events, or a rejection
export function reportProblem(_nothingYet: undefined, input, { actor, clock, newId }: DecisionContext<ReportingPerson>): Decision<ProblemReport, ProblemReported, "description-required"> {
  const description = input.description.trim();
  if (!description) return { ok: false, error: "description-required" };
  const report = { id: newId(), machineId: input.machineId, description, reporter: reporterOf(actor), reportedAt: clock.now() };
  return { ok: true, state: report, events: [{ type: "EVT-ProblemReported", problemReportId: report.id, … }] };
}

// report-problem-command.ts – the command
export const reportProblemCommand = aggregateCommand({
  id: "CMD-ReportProblem",
  allowedActors: reportingActors,                        // ["visitor", "helper", "technician"] as const
  store: problemReports,
  creates: true,                                         // a creating command: no load, saved at version 0
  decide: reportProblem,
  journal: repairEvents.journal,                         // the module's event catalogue (see *The event journal*)
  result: (report) => ({ problemReportId: report.id }),
});

// a command on an existing aggregate names it and the version the acting person saw
aggregateCommand({ …, target: (input) => ({ id: input.problemReportId, version: input.version }), decide: (state, input, context) => … });

// src/app/…/actions.ts – a Server Action only calls the runner (see *Server Actions and forms*)
const reportProblem = formAction(reportProblemCommand, { fields, input, onSuccess });
```

Rules:
- **One aggregate per command** (Q12): a command changes (or creates) the aggregate of its `store`. Its decision may also create **new aggregates of the same module** – `created: [created(defects, newDefect)]` – saved in the same transaction. Anything else (another existing aggregate, another module) goes through a policy or `context.run` (below).
- **A command that runs another** (`context.run`, Q6, built in ST-018): declare it with `runs: (state, events, input) => [run(otherCommand, input)]` – the layer runs it after saving, **as the same acting person**, in the same transaction, after that command's own authorization check (a person it does not allow makes the whole command `not-authorized`). Its rejection rejects everything; its error codes become part of the outer command's result type (so a form needs texts for them – the type check says so). Another module's command is imported through its `index.ts`. Example: CMD-RecordDefect runs Collection's CMD-ChangeMachineStatus (`src/modules/repair/record-defect-command.ts`); the inner command still needs the version the person saw – the form posts it. `runs` run before `policies`; `context.runAsSystem` stays for automatic policies only.
- **Facts on an existing aggregate** (ST-018): a changing command may declare `facts: (tx, input, state) => Promise<Facts>` too – read after the aggregate is loaded, passed as the decision's fourth argument (`decide(state, input, context, facts)`). CMD-RecordDefect reads the machine's status from Collection this way, so "only a stricter status" stays in its pure decision. A fact about **another aggregate of the same module** that must stay true until the commit locks its row there (ST-022: CMD-LinkProblemReportToDefect reads the chosen defect `FOR UPDATE` in `linkingFacts`, so a concurrent resolution waits – `link-problem-report-to-defect-concurrency.integration.test.ts`); another module's data is still read without a lock (below).
- **The decision is pure**: no database, no `new Date()`, no `randomUUID()` – the acting person, clock and ID generator come in its context. Rules with many cases get a table test at the decision (seam catalog).
- **Journal mapping** through the module's **event catalogue** (`src/modules/<module>/events.ts`, ST-079, architecture review 2026-10-17): a command passes `<module>Events.journal`; a new event gets its entry there first – references and non-personal facts only (see *The event journal*).
- **The acting person's type follows from `allowedActors`** (Q5/Q20): `aggregateCommand` infers the literal list, and the decision gets `DecisionContext<ActorOf<…>>` – a command for `["helper", "technician"]` gets `{ kind: "team-member"; teamMemberId: TeamMemberId; role: Role }` without narrowing; one that also allows visitors gets the union. Write the list once as `as const` next to the decision when the decision names it. `Actor` stays the technical type; `Role` (command layer) and `Reporter` (problem report, derived from the acting person in `reporterOf` only) are defined once – lint refuses a second definition. Every "… by" is a `TeamMemberId`.
- **Policies** the command triggers are declared with `policies: (state, events) => [trigger(policy, input)]` (see *Automatic policies*).
- **Set-based rules** (ST-007, HS-17): a creating command whose decision must know about the module's other aggregates declares `facts: (tx, input) => Promise<Facts>`; the layer reads them in the command's transaction and passes them to `decide(facts, input, context)` in place of the missing state. Facts that must stay true until the commit take a lock there – CMD-RegisterMachine takes `pg_advisory_xact_lock(hashtext('museum-number'))`, so concurrent registrations run one after the other – and a unique constraint stays the final guarantee (`museum_number`'s primary key).

**A command that some forms send with more than others** (ST-023): CMD-ReportProblem takes an optional triage part.
It is one command object with two typed names – `reportProblemAndTriageCommand` (the full input and every error) and
`reportProblemCommand` (no triage part, so none of the triage outcome's errors; what visitor and helper forms use) –
so a form needs texts only for the rejections it can cause. The decision is layered the same way:
`reportProblemAndTriage` runs `reportProblem` first, then the triage outcome's own decision (`recordDefect`) on the new
problem report, so the rules of both commands apply unchanged and the order of rejections is fixed (reporting first).
Since ST-052 the triage part is one of three outcomes (`defect-recorded`, `linked`, `resolved-on-the-spot`): the
decision checks who may choose which – resolving on the spot every team member, the others technicians only, else
`not-authorized` – and dispatches to that outcome's own decision; the command's facts add the chosen defect, locked as
in CMD-LinkProblemReportToDefect. Each triage event has **one** journal projection in Repair's event catalogue, used by its own command and by
CMD-ReportProblem alike. On the pages, the three forms that report and triage in one step share `ReportSection`, the
rejection text and the photo marker in `…/[museumNumber]/melden/`; the defect's fields and their input function live
beside the routes (`src/app/(team)/team/defect-fields.tsx`, `defect-input.ts`). The machine record confirms such a
problem report from the ID in the address, only when it is stored for that machine (`triaged-when-reporting.ts`).
A creating command may return `created` aggregates and `runs` like a changing one. Two rows that refer to each other
and are inserted together need one of the two foreign keys `DEFERRABLE INITIALLY DEFERRED` (hand-written migration,
`drizzle/0014_…`: the defect's reference to its problem report).

**A command behind a single button** (first: CMD-ClaimDefect, ST-025): the button is a small client form that posts
the version its page showed (`defect-button-form.tsx`). Whether the control is offered is the command's own rule: the
decision's reasons for refusing are one function next to it (`claimRefusal(defect, actor)`), which the decision applies
and Repair's `defectActionRefusals` asks for the team member looking at the page (below) – no second copy of the rule
in the page (G11). What a confirmation names but the aggregate does not keep (whom a defect was taken
over from) is a reference in the event's journal data, listed in `events.yaml` and in the catalogue, and read back typed with
`readJournal` (`lastDefectActionBy`) – only for the confirmation, never taken from the address.

**What a team member can do to a defect** (architecture reviews 2026-10-11, 2026-10-18): `src/modules/repair/defect-actions.ts`
describes each action on a defect once, in the order the page offers them (`defectActions`): its command's reason for
refusing a team member (built from the refusal function next to each decision), the event it ends in and what its
confirmation names from that event's journal data; its command sits next to it in `defect-action-commands.ts` (a file of
its own: the commands load the defect store, which asks the refusals). `defectDetails(db, id, teamMember)` returns the
refusals as `actions`; the defect's page shows what is `offered`, and a form page reads the defect with
`defectForAction(db, id, teamMember, action)` – the defect as its store loads it, its version and that command's refusal
– and shows the reason in place of its form (`defect-form-data.ts`) – no page carries a rule or a `can…` flag of its own
(G11). What a form may **offer** comes with it as `offer` (architecture review 2026-10-25, `defect-form-offers.ts`): the
assignees CMD-ClaimDefect would accept, the priorities CMD-PrioritizeDefect would accept, whether the team member may
choose a stricter machine status while reopening, whose claim removing the mark would release – each from the
command's own rule, which stays inside Repair. A new choice on a form is a new entry there, never a filter in the page.
In the app, `defect-action-pages.ts` says how each action looks – its form page (folder, button text) and its
confirmation text –, and every Server Action of a defect runs through `defectFormAction(action, { fields, input })`
(`defect-action.ts`): the access check, the action's command, then `/team/defects/<id>?done=<action>`. The page reads
`done` back only as an action there is (`doneActionOf`) and confirms it only when the defect's latest journal event is
that action by the team member looking at it (`lastDefectActionBy`) – never from the address alone, and without a state
field per action. **A new command on a defect** adds: its description and command in Repair, its journal projection in
`repairEvents`, its entry in `defect-action-pages.ts` and – if it needs input – its form folder, whose `actions.ts` only
says which fields it reads and how they become the input.

**What a team member can do in maintenance** (architecture review 2026-10-18): the same answer from Maintenance –
`dueMaintenance(db, clock, teamMember)` says on each due machine whether CMD-RecordMaintenance would accept them
(`recordOffered`), and the form page asks `maintenanceForRecording(db, clock, taskId, machine, teamMember)` for the
task, the refusal (`whyNot`) and the dates allowed. The page keeps no rule of its own (G11); `recordRefusal` stays
inside the module.

**Maintenance's lists read Collection's machines themselves** (architecture review 2026-10-25): Collection publishes
its machines for maintenance (context map, Published Language), and the answers over them read them in one call –
`dueMaintenance`, `maintenanceForSeveral(db, clock, taskId, teamMember)` and `machineMaintenance(db, clock, machineId,
{ teamMember, latestRecordCount })`, the machine record's section 5 (due tasks, Not on display, the newest records). No
page passes `machinesForMaintenance` in – the exception to "the page composes" below, as a downstream context reading
its upstream's published query, the way a command's facts do. A retired machine is not published for maintenance:
nothing is due on it. The one machine of the recording form stays the page's (`maintenanceForRecording` above): it comes
from the address, and the page checks it where it reads it.

**What a team member can do on the machine record** (architecture review 2026-10-18): `loadMachineRecord(db, museumNumber,
{ clock, viewer })` returns `actions` – report a problem, change the location, change the status (Collection's
`machineStatusesToChangeTo` for the viewer's role), attach a file – and the view shows only those; neither the page nor
the view takes a `can…` prop. An offer another module decides per item (ST-047's „Wartung erfassen“ per due task) comes
with that section's data from that module.

**A confirmation after an action (G3)** – one rule on every team page (architecture review 2026-10-18): the address
only says *what* to look for (`?statusChanged`, `?done=claim`, `?defectRecorded=<problem report>`, `?recorded=<id>`,
`?registered=`, `?created=`, `?corrected`, `?added=`, `?changed=`, `?removed=`); the page confirms it only when `lastCommandBy(db, { machineId } |
{ aggregateId }, viewer)` (command layer) says the latest command on that target was that action **and** the team
member looking at the page ran it. The command layer gives every journal entry its command's ID
(`event_journal.command_id`), so the answer holds every event the command wrote – a status change made in the same step
is confirmed from there, never from a flag in the address. Which events mean what stays the owning module's: each
module answers typed questions about a command (`collectionChangesIn`, `machineRegisteredIn`, `machineModelChangeIn`,
`fileAttachedIn`, `triageOutcomeIn`, `problemReportedIn`, `maintenanceRecordedIn`, `maintenancePlanChangedBy`), built on
`entriesOf(<module>Events, command)` – no page matches an event type by string. The triage outcomes share one module,
`src/app/(team)/team/triage-confirmation.ts` (triage list and machine record); the machine record asks
`loadMachineConfirmation` and shows one `confirmation`; the defect page's `lastDefectActionBy` asks the same latest command.
**The one exception** is the visitor's report form (`/m/<museum number>?gemeldet=1`): a visitor has no account, so there
is nobody to bind the confirmation to – it says only that a report was sent, nothing stored.

**Where an action sits on the defect's page** (G22, first: ST-026): the work – `claim`, `release`, `log-work`,
`resolve` – as buttons under the header; what manages the defect behind the fold „Verwalten“ (`manage-defect.tsx`, a
native `<details>` that a rejection opens). One command can be two actions – CMD-ClaimDefect is `claim` and, with
`assignTo`, `assign` – and one action can sit in two places: releasing one's own claim stands where „Übernehmen“ stood,
releasing someone else's behind „Verwalten“. A one-tap action is a `DefectButtonForm` with `defectVersionInput`. A
choice of team members is Repair's offer (`offer.assignees`: Team's active team members filtered with the command's
own rule per team member, `assigneeRefusal`, by ID – the page names them); the command reads the chosen team member's
role itself (`activeTeamMemberRole` in its facts) – it never trusts the list. A form whose empty choice would mean something else (no `assignTo` is a claim of one's own)
sends the empty value, so the command rejects it.

**An action on a defect that needs input** (first: CMD-ResolveDefect, ST-028 – G21): a button-styled link on the
defect's page leads to a form page of its own (`…/defects/[defectId]/beheben/`, `…/arbeitsschritt/`), which repeats the
defect, loads only what it shows (`loadDefectForForm(db, defectId, viewer, action)`) and lands on the defect's page. The
form page shows the command's reason in place of the form to someone it would refuse, unless there is an action state to
keep.

**Two transactions racing for one row** in a test: `whileHoldingRow(db, sql\`SELECT … FOR UPDATE\`, race)` from
`src/test-support/held-row.ts` – it counts only the sessions blocked by its own holding transaction, so tests running
beside it in the shared database cannot disturb it, and it lets go also when the test throws.

**A rule that needs another module's data** (first: ST-013, context map "Repair reads from Collection when checking
command rules"): the command's `facts` call the other module's **public** query in the command's transaction – e.g.
`reportingFacts` in `src/modules/repair/problem-reports.ts` calls Collection's `machineForReporting(tx, machineId)`
– and the decision gets the result as plain data. The query is as narrow as the rule (a machine status and whether it
is retired, not the machine). Only a context the context map names as upstream is read this way; nothing is stored
twice, and the other module's tables are never imported. Such a read takes **no lock**: it is a check against the
current state at command time, not an invariant (context map). **The one exception is "is the machine retired?"**
(ADR 0010, ST-039): Collection's `machineForReporting` and `machineForMaintenance` take the machine's retirement lock
shared (`retirementLock`, a transaction-scoped advisory lock), CMD-RetireMachine takes it exclusively – so a command in
flight finishes before the retirement's policies look, and one that starts meanwhile waits and reads *retired*. **A new
command that creates or reopens something on a machine reads the machine through one of these two** (or a new
Collection read taking the same lock), and before any row lock of its own – the advisory lock always comes first.

**Histories are append-only lists** (architecture review 2026-09-27, Q13; built in ST-012; the store keeps them since
the architecture review 2026-10-11). A history – the machine status history, a work log, defect resolutions – is a list
in the aggregate's state; the decision appends an entry with an ID from `context.newId()` and never changes or removes
one. The module describes it once – `history({ table, owner: "defectId", toEntry, toRow })`
(`src/platform/command/history.ts`) – and names it in its store under the name of the list in the state:
`aggregateStore({ …, histories: { workLog, resolutions }, toState: (row, histories) => … })`. The store loads the lists
into the state (the oldest entry first), and saves them with the aggregate: it inserts the entries whose ID is not
stored yet and never updates or deletes a stored entry, whatever the state says about it. No module writes a store by
hand for a history. A history table has its own `id` (the entry's ID, no database default), the owner column and a
`position bigserial` for the order entries were stored in (entries of one command share their point in time).
- **A fact that comes later is an entry of its own** – a reopening after a resolution (data model, ST-030) is appended
  as a *Reopening*, never written onto the stored *Resolution*; the page puts the two in order.
- **A list inside a history entry** (the photos of a work log entry, ST-032) is a history of its own on the aggregate,
  each entry naming the entry it belongs to – the store has no nested lists.
- **Read models load a history through its description** – `workLog.load(db, defectIds)` gives the entries of many
  aggregates in one query, by aggregate ID (the repair history of a machine, ST-033) – and never map the rows a second
  time.
- **A list of entities that are changed** (the maintenance tasks of the maintenance plan, built in ST-040) is not a
  history: `entities({ table, owner, toEntity, toRow })` (`src/platform/command/entities.ts`), named in the store under
  `entities: { maintenanceTasks }`. It is loaded like a history; saving inserts the entities not stored yet and updates
  only the stored ones whose columns differ. **Nothing is ever deleted** – an entity that ends is marked in its own
  columns (a removed maintenance task keeps `removed_at`, ST-041), and one the state leaves out stays stored as it was.
  Proven by `src/platform/command/entities.integration.test.ts` (a stand-in aggregate, a trigger refusing DELETE, a
  count of UPDATEs). `History` and `Entities` are both a `StoredList` – the store treats them alike, each says in its
  `kind` what saving means.
Examples: `defects.ts`, `machines.ts` (which wraps its store only to keep the museum number register). Proven by
`src/platform/command/history.integration.test.ts` (a stand-in aggregate, with a trigger in its own database that
refuses UPDATE), the machine status history test in `change-machine-status-command.integration.test.ts` and
"ST-024: Work log entries cannot be changed". The real tables get no such trigger: an entry's free text (a reason) may
one day have to be removed.

What `executeCommand` (`src/platform/command/index.ts`) guarantees – don't re-implement any of it:
1. **Authorization first**: the actor must be in `allowedActors` (`"visitor" | "helper" | "technician" | "system"`), else `not-authorized` before the command runs. Role rules beyond that (e.g. "only the claimant") are domain rules in the decision.
2. **One transaction** for all changes and journal entries; a rejection, `version-conflict` or `not-found` rolls everything back.
3. **One point in time**: `clock.now()` is the same for the whole command, its events and its policies.
4. **Every successful command journals at least one event** – `events: []` from a command is a bug and throws.

Results: `{ ok: true, result }` or `{ ok: false, error }` where `error` is the decision's own reason (kebab-case, shown via the message catalog) or `not-authorized` / `not-found` / `version-conflict`.

The **actor** comes only from `currentPerson()` in `src/app/_actions/current-person.ts`, which **reads the session of the current request** (ST-069): a signed-in team member with the role stored now – read again for every command, so a role change applies to the next action – or a visitor when there is no session or an expired, unknown or forged one. Never from form data. The **session of a deactivated account** acts as nobody, not even as a visitor: the Team module ends the session and throws `DeactivatedAccount`, `currentPerson()` redirects to `/login`, so the command never runs. `currentPerson()` is for Server Actions only (ending a session sets a cookie); pages use `requireTeamMember()`. **The system actor never comes from a session** – automatic policies run only through `context.runAsSystem` (ST-003). Tests call `executeCommand` with an explicit actor.

## Server Actions and forms

The Server Action runner (ST-073, architecture review Q9/Q10/Q18/Q19) is the only way from a form to a command.

```ts
// src/app/…/actions.ts ("use server") – exports only async functions, so the runner goes into a local constant
const registerMachine = formAction(registerMachineCommand, {
  fields: registerMachineFields,                           // the form's own fields – only these are read and echoed
  input: registerMachineInput,                             // FormFields → command input
  onSuccess: async ({ machineId }) => { revalidatePath(…); redirect(`/team/machines/${machineId}`); },
});
export async function registerMachineAction(previous: RegisterMachineState, formData: FormData) {
  await requireTechnician();                               // the page's access check – before the runner
  return registerMachine(previous, formData);
}

// the form – a client component
const [state, action, pending] = useActionState(registerMachineAction, null);
// state: null, or { error, values } after a rejection → rejectionText(state.error), defaultValue={state.values.x}
```

- **A Server Action that runs a command only calls the runner.** (Login, logout and the ST-005 account actions call Team module functions backed by Better Auth, not commands – they take the acting person from the same `currentPerson()`.) `formAction` (`src/app/_actions/form-action.ts`) takes the acting person from `currentPerson()`; it has no parameter for an actor, a role or a team member ID, and form fields named `actor`/`role`/`teamMemberId` are never read. Lint refuses `executeCommand` and the factory `formRunner` anywhere under `src/app/` outside `_actions/` (tests excepted).
- **`{ error, values }` with `useActionState`**: on a rejection the action returns the error code and the typed values of the declared fields; the form shows the catalogue text and keeps the input. Success goes through `onSuccess` (usually `revalidatePath` + `redirect`), which also empties the form. It works without JavaScript – key the field on the state so React's form reset does not drop the kept value.
- **One small typed input function per action** (Q19), no schema library: it reads and converts the fields, domain validation stays in the decision. **The empty-field rule:** a missing or empty field becomes "no value given" and the decision decides – a text field an empty string; a field that is not free text `undefined`. Example ST-007: a missing machine model becomes "no machine model given", which CMD-RegisterMachine rejects ("Machine model and location are required"); a missing museum number – optional there – becomes "no museum number given" and the command assigns one. The input function **never fills in a default** and never throws; an unknown enumeration value is "no value given" too. This holds for every form on the runner; the ST-005 account actions predate it (their `role()` helper falls back to helper) and follow it when they move onto a command.
- **A form on an existing aggregate** (first: ST-012, `…/[museumNumber]/status/`) posts the aggregate's ID and the
  version its page loaded as hidden fields; the page reads them with a query that returns the version (e.g.
  `machineForTeamForm`). The form renders the version with `<VersionField version={…} />` and keys every field that
  keeps its value on `keptKey(state)` (`src/app/_actions/form-parts.tsx`); the input function reads it with
  `versionSeen(fields.version)` (`src/app/_actions/version.ts`) – a version that is not a whole number is `-1`, a
  version nobody saw, which the command layer answers with `version-conflict`. No form writes these three by hand
  (architecture review 2026-10-11). **Every Server Action re-renders the page it
  was posted from** (`currentPerson()` renews the session cookie, and a cookie change makes Next.js re-render the
  current route in the action's response – ST-019 review, 2026-10-05). So after a rejection the form posts the version
  stored *now*, not the one the page first loaded. That is safe because the decision runs first: a domain rejection
  ("already triaged by Tom") explains a change made in between before the version is compared (*Version check*). A
  form must therefore never rely on the first loaded version, and a page must **not swap its form for a "nothing to
  do here" text when the aggregate changed meanwhile** – the form would unmount and drop the input and the rejection.
  Render the form and let it show such a text only when there is no action state yet (`triaged && !state`, the triage
  forms of ST-018/ST-019).
- **A public page posts no internal ID** (first: ST-013, the report form): the page binds the museum number –
  `reportProblemAction.bind(null, museumNumber)` – and the action finds the machine on the server
  (`machineIdOf`) before it builds its `formAction`; the redirect uses the same museum number, URL-encoded under a
  fixed path. A bound value comes back from the browser like a form field, so it is treated as one: it only names
  which machine, and the command checks that machine again in its facts. Team pages may post IDs (`machineId`,
  `version` in ST-012).
- **A client form gets only strings from a catalogue**: a visitor catalogue holds functions (`alreadyReported`), which
  cannot cross to a client component – pass the sections the form shows (`{ reportForm, commandErrors }`).
- **Never declare a password (or another secret) in `fields`** – the declared fields are sent back to the browser after a rejection. A form with a password field gets an option to keep it out of `values` when it first moves onto the runner (ST-073 code review).
- Page access checks (`requireTeamMember()`, `requireTechnician()`) run in the Server Action before the runner – authorization proper stays in `allowedActors`.
- **One runner, an optional content step** (architecture review 2026-10-18): every form calls `formAction(command, definition)`; the definition chooses the step – none, `photo`, `upload` (below) or `each`. There is no second runner.
- **A form that runs its command once per chosen item** (first: ST-045, one maintenance task on several machines) passes
  `each: { field }` – the field the browser posts once per ticked native checkbox – and `input: (fields, item) => …`.
  The runner runs the command for each item in its own transaction, one after the other, so one item's rejection
  does not stop the others; `onSuccess` gets `{ done, rejected }` once at least one was done. Nothing ticked is
  `nothing-chosen`; when every item is rejected the form stays (`EachFormState`: the ticked `chosen` items, and
  `rejected` per item only when the reasons differ). The page landed on confirms each record by `lastCommandBy` (G3);
  the items left out are named in the address, but their reason is the owning module's answer now – never the address's.
- **A form with a photo** (ST-016) passes `photo: { field, owner }` and `input: (fields, photo) => …`: the command runs through the photo module's `withStoredPhoto` – a rejected or throwing command leaves no stored photo, and a photo that cannot be accepted or stored (`too-large`, `not-an-image`, `unsupported-format`, `not-stored`) comes back as `{ error, values }` like a command rejection. The form state type is `PhotoFormState<CommandError<typeof command> | PhotoError, Field>`; the photo errors have texts in every catalog. The form shows `PhotoField` (`src/app/photo-field.tsx`), keyed on the state like the text fields.
- **After a rejection the photo must be chosen again** (UX guideline G8a; ST-023, ST-084): the browser cannot put a
  file back into the form. The runner's photo step marks the state `photoAgain: true` – a photo was attached and the
  rejection is not one of the photo errors, whose texts already say what to do – and the form's rejection text adds
  the catalog sentence: `photoRejectionText(state, overrides?)` on team forms (`src/app/_actions/rejection-text.ts`,
  `teamMessages.forms.photoAgain`), `reportRejectionText` on the visitor's report form (`reportForm.photoAgain`).

## Photos and stored content (ST-016, ADR 0009 – superseding ADR 0007)

- **A photo is stored only through the photo module's `withStoredPhoto`** (store → run the command with the reference → delete if it fails) – in a Server Action via `formAction` with a `photo` step. Nobody calls the storage seam's `write` for a photo directly.
- **The storage seam** (`src/platform/storage/`, `ContentStorage`: write, delete, `viewAddresses` – one call per page –, and since ST-085 `uploadAddress` and `size`) is injected like the clock and the ID generator: `blobStorage()` in production (the only file that may import `@vercel/blob` – lint), `memoryStorage()` in integration tests. A page data function takes `{ storage }` with `blobStorage()` as its default (`PhotoSource`); a runner takes `storage`.
- **Names and times come from the injected generator and clock:** `<owner>/<newId()>.jpg`; view addresses are valid 5 minutes from `clock.now()` (`photoViewAddresses`).
- **A failure of the storage never breaks a page or hides an answer:** `photoViewAddresses` gives no addresses when Blob cannot sign (the page shows its reports without photos), and a failed cleanup delete after a rejected command still returns the rejection (the photo stays behind unreferenced, ADR 0007).
- **Only team pages issue view addresses** (HS-1); a visitor page's data never holds a photo reference. A team page shows a photo with `ProblemReportPhoto` (`src/app/(team)/team/problem-report-photo.tsx`).
- **Deleting content is irreversible** (no restore in Blob): only for deliberate removal (spam dismissal, ST-020) or a failed command – never as a compensation after a committed one.
### Files uploaded from the browser (ST-085, ADR 0009)

Files (up to 100 MB, `FILE_SIZE_LIMIT`) never pass through a function: the browser uploads them straight to the private
store before the attaching form is sent. The upload module (`src/upload/`, below the modules like the photo module) is
the only way:
- **Two steps, one route** (`src/app/api/uploads/`): the browser half `uploadFile(file, { owner, onProgress })`
  (`src/upload/browser.ts`) first asks the route for a name (`recordPendingUpload`: the server names the content
  `files/<newId()>` and records a **pending upload** – owner, team member, time, size limit), then the Blob client
  library's `uploadPresigned` asks the same route for the upload address of that name (`uploadAddressOf`: only for
  the team member it was recorded for, valid 30 minutes). It resolves with the name – what the attaching form sends –
  or `too-large` / `not-uploaded`, which the form shows instead of attaching nothing. A request may ask for a
  **stricter** limit than 100 MB (the browser tests do), never a larger one.
- **The route is not behind the page proxy** (`/api/` is not matched): it checks the Origin (`isSameOrigin` from
  `src/platform/same-origin.ts`, shared with `src/proxy.ts`) and the team session itself, before anything else. It
  is written as `uploadRoute(dependencies)` so its tests can pass real requests and the in-memory storage.
- **Attaching** (CMD-AttachFile, ST-037) goes through `withUploadedContent(dependencies, { name, owner }, run)`: it
  takes the pending upload (same owner, younger than 24 hours – a row-level delete), checks the stored size, runs the
  command with the name and deletes the content if the command is rejected or throws. Its own rejections are
  `uploadedContentErrors`: `content-gone` (no such pending upload, or nothing uploaded – the form says to choose the
  file again) and `too-large`.
- **Blob holds only an upload in one piece to the size limit.** An upload in parts (above 20 MB, multipart) is not
  checked against `maximumSizeInBytes` – found in ST-085 with a 25 MB file under a 21 MB limit. So the size is
  checked when attaching (`storage.size`), and content above the limit is deleted and refused.
- **Abandoned uploads** – a form never sent – are cleaned up by `cleanUpAbandonedUploads`: after the response of every
  name the route gives (`after()`), at most 20 pending uploads older than 24 hours, the oldest first, each deleted with
  its content in one transaction (a failed content deletion keeps the record for the next time). No scheduler (ADR 0002).
- **Opening uploaded content**: `viewAddressOf(storage, clock, name, { download })` – 5 minutes, only after the
  page's access check; the plain store address answers 403. A file has an address of its own,
  `/team/dateien/<file ID>` (ST-037, a route handler): it checks the team session and sends the browser on with 303
  to a fresh 5-minute address, so a link on a page never expires. Only PDF and JPEG/PNG/WebP/GIF open in the browser
  (`opensInBrowser`, by the media type the store kept); everything else gets Blob's `download=1`.
- **A form that attaches uploaded content** (first: ST-037, `…/[museumNumber]/datei-anhaengen/`) uses
  `formAction(command, { fields, upload: { field, clearedWith, owner }, refusal, input, onSuccess })`: the
  chosen file is uploaded when it is chosen (`uploadFile`), the form posts its name in a hidden field. `refusal` – the
  command's rules that need only the fields (`attachFileRefusal`) – is asked first and keeps the uploaded content: the
  form says the chosen file is still attached (user, 2026-10-18). Every later rejection (`content-gone`, `too-large`,
  the command's own) deletes it, the state no longer names it, and the form says to choose it again (G8a).
- Locally the dev server and the browser tests use a separate Development Blob store (`BLOB_READ_WRITE_TOKEN` in `.env.development.local`); without it the photo browser tests skip.

## The event journal

`event_journal` (`src/platform/schema.ts`) – append-only, a database trigger refuses UPDATE/DELETE/TRUNCATE. The layer writes type, time, actor (kind, team member, role), aggregate, machine and `data`.

- `data` holds **only references and non-personal facts** (a new status, a priority, a defect ID) – **never free text a person typed** (descriptions, notes, reasons). Text lives only in the aggregate, where it can be removed (spam dismissal, personal data). Decided 2026-09-27.
- Set `machineId` whenever the event concerns a machine – timelines and "new since last visit" (ST-050) query by it.
- **The event catalogue per module** (`src/modules/<module>/events.ts`, `eventCatalogue` from the command layer; ST-079, architecture review 2026-10-17): per event type its aggregate and its projection – the aggregate ID, the machine and the only fields that reach the journal. Commands pass `<module>Events.journal`; `events.test.ts` next to each catalogue checks it against `events.yaml` (the event exists there, on its own aggregate or on that of a command producing it).
- Read it typed with `readJournal(db, <module>Events, { types, aggregateIds, machineId, since, notBy })` – the data of each entry is typed by its projection (partial: older entries may lack a later field); `journalOf(db, { aggregateId } | { machineId })` stays for tests and untyped looks. It is never replayed to rebuild state.

## The Last visit – per-member state that is no command (ST-050, ADR 0011)

The one exception to "every write is a command that journals": opening the dashboard is no domain fact. The Team
module keeps one row per team member (`dashboard_visit`: when the current visit began, the Last visit) and the pure
rule `decideVisit(stored, now)` – one visit lasts while the dashboard is opened again within an hour of its beginning
(user, 2026-10-24, decision 3: a table of its own with a conditional write, no `aggregateStore`, no `AGG-` ID).
- **One writer, from the client:** `VisitRecorder` (`src/app/(team)/team/visit-recorder.tsx`) calls
  `recordVisitAction` from a `useEffect` – never the page render, which also runs on a prefetch and on the re-render
  after every Server Action. The action takes no input; whose visit it is comes from `currentPerson()` alone.
- **The write keeps one visit:** `recordVisit` writes only when a visit begins – the first insert `ON CONFLICT DO
  NOTHING`, a new visit only over the one it read – so a reload, a second tab or two devices at once change nothing twice.
- **A dashboard reads, never writes:** its data function takes `markLineOf(db, clock, viewer)` (Team's `lastVisitOf` –
  the same rule, computed) and marks with `isNew(marks, at, by)` (`new-since-last-visit.ts`). Its 7-day window
  is `recentSince(clock, backTo?)` – the technician dashboard's recent changes start there and reach back to the Last
  visit (it passes its mark line); on the helper dashboard it only bounds how long a defect that left her stays listed
  (no mark line passed). A module query takes that instant (`changesOnClaimedDefects(db, since, …)`), never a window of
  its own. A mark is after the Last visit and not the viewer's own doing, by actor. The mark is `NewMark` („· neu seit
  deinem letzten Besuch“, G6a). Tested at the data function with an open = render first, then `recordVisit` (`technician-dashboard-new.integration.test.ts`).
- Not every Server Action goes through `formAction`: this one runs no command. Every other write still does.

## Version check (HS-16)

Every aggregate table has `version integer not null default 0`; `aggregateStore` is the only place that reads or checks it. A page shows the version it loaded, and a command on an existing aggregate passes it in `target`. The layer then (Q11):
1. loads the **fresh** state (`not-found` if there is none);
2. lets the decision run on it – a **domain rejection comes first** ("already triaged by Eva", ST-018), because it explains more than a conflict;
3. saves at the **version the acting person saw** and increments it – `version-conflict` when someone changed the aggregate in between and nothing domain-specific explains it. **When the save fails the version check, the layer loads what is stored now and runs the decision again** (ST-018): a domain rejection there wins – the second of two technicians triaging at the same moment gets "already triaged", not a conflict (`src/modules/repair/record-defect-concurrency.integration.test.ts`, two real transactions). The facts are read again for that second decision. It relies on PostgreSQL's default isolation, READ COMMITTED: after the failed `UPDATE` waited for the other transaction, the next read sees what it committed – a stricter isolation level would need a retry instead.

Creating commands save at version 0. A command run by a person **must** pass the version in `target` – the layer refuses it otherwise. Only policies (run by the system) may leave the version out of `target` – then the aggregate is loaded with a row lock (`FOR UPDATE`), so concurrent policies wait for each other instead of failing with a conflict nobody caused. A decision that returns **no events** has done nothing: nothing is saved and the version stays. Required for every triage command and every command on a defect (ST-003).

## Automatic policies

A policy (`POL-…`) is an `aggregateCommand` allowed for `"system"` only. The triggering command declares it; the layer runs it **after saving, in the same transaction**, as the system:

```ts
policies: (report) => [trigger(somePolicyOfThisModule, { problemReportId: report.id })], // a policy of the same module
```

Its events are journaled with the system as actor, after the triggering command's events. A rejected policy rejects the whole command. A policy may journal nothing when there is nothing to do.

**A policy of another module** (ADR 0010, first: ST-039): the upstream command never names a downstream policy. The
downstream module adds them – `withPolicies(command, [policy({ id: "POL-…", calls: async (tx, { events, actor }) =>
[trigger(…)] })])` – a policy reads what happened from the triggering command's journal events, never from its result
(which is the page's) (`src/platform/command/policies.ts`) – and exports the result; the page uses that export (CMD-RetireMachine
with Repair's two policies: `src/modules/repair/retirement-policies.ts`). A policy that acts on many aggregates selects
them `FOR UPDATE`, filtered by the state it acts on, so one changed a moment earlier is skipped instead of rejecting the
command; each is then changed by its own command, run as the system without a version. When a second module reacts
to the same command, the composition moves to a neutral element (ADR 0010, option 4).

## Read models

A read model (`RM-…`) is a query function in the owning module, exported via `index.ts`, e.g. `problemReportsOfMachine(db, machineId)`. It takes a `Database`, returns plain data for the page and selects only what the page shows. Read models are computed on read – no projections (ADR 0002).

**Not every query is an `RM-…`** (user, 2026-10-01, during `/implement` ST-006): a query that only feeds a choice or a detail *inside* its own bounded context carries no domain ID, because `events.yaml` names only the read models that are a view of their own – `machineModelsToChooseFrom` (the machine models the registration of ST-007 chooses from) is one of those. Don't invent an `RM-…` for it; a query that does become a screen gets its ID from `events.yaml` first, through the domain-architect.

**Reading across modules – the page composes** (decided 2026-10-02, ST-009): a page that needs another module's
data calls each module's own public query and puts the results together in its page data function – e.g. the
machine record (`src/app/(team)/team/machines/[museumNumber]/machine-record-data.ts`) takes the Collection module's
`machineRecord` (with TeamMemberIds) and the Team module's `teamMemberNames(db, ids)`. Neither module imports the
other, and there is no database view across modules. A module offers such a query as narrow as the page needs (names
by ID, not its table). Don't import another module's `schema.ts`. The one exception: Maintenance reads Collection's
machines for maintenance itself (see "Maintenance's lists read Collection's machines themselves").

**Naming what read models return by ID** (architecture review 2026-10-25): a team page names the team members and
machines its read models refer to only through `named(db, ...parts)` (`src/app/(team)/team/named.ts`) – Team's
`teamMemberNames` and Collection's `machineLabels` in one round for all parts of the page, each part a `References`
(`{ teamMembers, machines }`, missing IDs left out; `openDefectReferences(defects)` for open defects). Its `name(id)`
says „unbekannt“ for an account that is gone – the one rule; its `label(id)` throws for a machine that is not there,
because read models only return registered machines (foreign keys) – a bug, never a blank. Shared shapes take the
result, not the database: `shownOpenDefects(clock, defects, named, viewer)`, `shownClaimant`, `shownReporter`,
`defectForForm`. An ID that comes from the address or a form is no read-model result: the page checks it where it
reads it (`machineIdOf`, `isId`) and labels it with `machineLabels` itself, where a missing machine is a case to show,
not a bug (`due-maintenance-data.ts`, `record-maintenance-data.ts`, `address-after-recording.ts`).

## Time and time-based rules

Never call `new Date()` in domain code – use the injected `Clock` (`src/platform/clock.ts`; `systemClock` in production, `fixedClock("2026-…Z")` in tests). All calendar logic goes through `src/platform/time.ts`:

| Need | Helper |
|---|---|
| "today", a Berlin calendar date (`YYYY-MM-DD`) | `today(clock)`, `calendarDate(instant)` |
| "waiting longer than 3 days" (72 h), "older than 14 days" (336 h) | `elapsedMoreThanHours(since, now, hours)` |
| where "the last 7 days" (168 h) start (ST-058) | `hoursBefore(instant, hours)` |
| the earlier of two instants – 7 days back or the Last visit (ST-050) | `earlierOf(a, b)` |
| month arithmetic, clamped to the month end | `addMonths(date, months)` |
| due date and first overdue day of a maintenance task | `maintenanceDates(lastDone, months)` |
| grace days from any start (e.g. the return to display, ST-056) | `graceDays(start, months)`, `addDays` |
| showing a time | `formatDateTime(instant)` → `15.01.2026, 10:05` (Berlin) |

Time-based states (due, overdue, stale claim, waiting) are **computed when a page loads** – no cron, no scheduler (ADR 0002).

## UI texts

- No text literals in pages. Team pages: `teamMessages` (German, `src/platform/messages/team/` – one file per area since the architecture review 2026-10-18: `shared.ts` for the terms, the form texts and the error codes several areas share, and one per bounded context – `accounts.ts`, `collection.ts`, `maintenance.ts`, `repair.ts` – with its pages' texts and its commands' error texts (`…Errors`), plus `dashboard.ts`; a new text goes into its area's file, a code that a second area starts to produce moves to `shared.ts`, and a test keeps every key and code in one file only. `commandErrors` is their flat merge – one text per code, no per-area override: a form that needs other words for a shared code passes them to `rejectionText(…, overrides)`, and a rejection that means something else gets its own code. The Team module's account functions are no commands; their reasons stay in `accountErrors`, outside `commandErrors`); domain terms under `terms`, keyed by the glossary term, in the `_UI (de)_` wording – a test compares them with `CONTEXT.md`. Add a term when a page first needs it.
- Visitor pages: `visitorMessages(locale)` – `visitor.de.ts` and `visitor.en.ts` have the same keys (type and test). The locale of a request (ST-010): `currentVisitorMessages()` (`src/app/visitor-locale.ts`) – the remembered switch (cookie `visitor-locale`, set by the Server Action `switchVisitorLanguage`, one year), else the browser's highest-ranked of German and English in `Accept-Language`, else English (`visitorLocale`, table test). Every visitor page is built on `VisitorPage` (`src/app/visitor-page.tsx`, ST-064), which sets `lang` on its content and shows `VisitorLanguageSwitch` at the top and the legal links (`/datenschutz`, `/impressum` only if the museum provides an imprint) at the end – never assemble that frame by hand.
- Command errors map to catalog texts by their kebab-case code: the `commandErrors` section of the visitor catalogues, read with `commandErrorText(messages, code)`. A form that shows `commandErrorText(messages, state.error)` fails the type check when one of its command's error codes (including `not-authorized`, `not-found`, `version-conflict`) has no text – the runner itself does not constrain the codes. A team catalogue section follows with the first team form (ST-007). **A team form on the runner shows `rejectionText(state.error, overrides?)`** (`src/app/_actions/rejection-text.ts`, architecture review 2026-10-17): the form kept the input and its page shows the aggregate as it is now, so a conflict asks to send again (`forms.conflict`, G8/G13); a form passes its own text for an error where it knows more (who triaged first, a machine retired meanwhile, log work's conflict). One-tap buttons have nothing to keep and show `commandErrorText` directly. An address that is no aggregate ID is checked with `isId` from the command layer.

## Security

- Every command goes through a **Server Action** – never a route handler. `src/proxy.ts` rejects any POST to a page whose `Origin` is missing or foreign (CSRF); Next.js checks the Origin again. Route handlers under `/api/` are not behind the proxy: they check the Origin themselves (`isSameOrigin`) and the session (the upload address route, ST-085), or their own signature. No route accepts Blob upload-completion callbacks.
- Authorization lives in the command layer, never only in the proxy or a page (ADR 0001).
- React escapes output; `dangerouslySetInnerHTML` is not used. Security headers: `next.config.ts` (a script CSP follows with ST-070).
- No personal data in logs or in the journal.
- **Login** (ST-004, ADR 0004/0006): Better Auth lives inside the Team module (`src/modules/team/auth.ts`) and is only called on the server – **never mount its HTTP handler** (no `/api/auth/*`): that would expose sign-up and the admin endpoints. Login and logout are Server Actions under the proxy's Origin check. Every team page and team Server Action calls `requireTeamMember()` itself (the `(team)` layout checks too, but layouts don't re-run on navigation). `BETTER_AUTH_SECRET` per environment (Vercel: sensitive, set by the user).

## Migrations

Change `schema.ts`, then `npm run db:generate -- --name <what>`; hand-written SQL (triggers) goes at the end of the generated file. A **foreign key to another module's table** is hand-written SQL in the migration too – a module's schema never imports another module's tables (e.g. `problem_report.reporter_team_member_id` → `team_member.id`). Migrations run in the Vercel build (`npm run db:migrate`) and in the test database reset. Locally: `npm run db:up`, `npm run db:migrate:dev`.

## Tests

| Tool | Command | Where |
|---|---|---|
| Vitest project `unit` | `npm test` (both projects) | `src/**/*.test.ts` |
| Vitest project `integration` | – | `src/**/*.integration.test.ts`, real PostgreSQL `laguardia_test`, dropped and migrated once per run |
| Playwright | `npm run test:e2e` | `e2e/*.spec.ts`, 360 × 800 – locally an own dev server (port 3100, distDir `.next-e2e`) against `laguardia_e2e_test`, or the preview (`BASE_URL`) |
| Everything | `npm run verify` (`--e2e` for browser tests) | lint, types, tests, traceability |

- **Titles:** every Gherkin scenario of a story has exactly one test titled `ST-NNN: <scenario title>` (checked by `verify.ts`). Tech-task tests describe behaviour without the prefix.
- **Things that exist** (architecture review 2026-10-11): what a scenario's "Given" names comes from `src/test-support/`,
  set up through the commands – `aRegisteredMachine(db, status)` (`machines.ts`), `anOpenDefectIn(db, { recordedBy, at,
  title, suitableForHelpers, machineStatus, priority })` (`defects.ts`, returns machine, defect and problem report IDs),
  `aDefectWithHistory(db, { by, recordedAt, title, priority })` for a defect whose history a test lays out step by step,
  each step at its own instant – `linkedReport`, `logWork`, `prioritize`, `resolve`, `reopen`, `retireMachine` (ST-051),
  `post(fields, photo?)` for a posted form (`forms.ts`). A test binds its database, acting people and clock once in a
  one-line helper of its own (`const anOpenDefect = (title) => anOpenDefectIn(db, { title, recordedBy: tom, at })`) – it
  does not copy the command call. A page test in an isolated database that needs "LG-042" of a given machine model
  still registers its machines itself.
- **Probes of the command layer** live in `src/modules/repair/command-probes.test-support.ts`: commands that do what
  no real command does (for the version check, the policies, the histories), and `storedProblemReport` /
  `storedDefect` for the few command tests that check a state no read model shows. Prefer the read model
  (`defectDetails`, `problemReportsOfMachine`) wherever it shows the fact; a real command is never stood in for.
- **Test data:** builders in `src/test-support/builders.ts` (`aMachine`, `aDefect`, `aHelper`, `aTechnician`, …) – override only what the test is about. Switch a builder to the real domain type when the aggregate gets one.
- **Time:** `fixedClock(…)` for every command and rule; `BUILDER_TIME` is the builders' default.
- **Acting team members exist:** a test actor `{ kind: "team-member", teamMemberId }` must exist as an account (foreign keys, ST-004): `anExistingTeamMember(db, actor)` from `src/test-support/team-members.ts`; accounts with a password come from the Team module's own test support.
- **Isolation:** integration tests share one database per run – give each test its own machine and assert on that, never on table counts.
- **A machine to refer to:** a problem report needs a registered machine (foreign key, ST-007) – `aRegisteredMachine(db)` from `src/test-support/machines.ts` registers one through the commands. Its journal starts with `EVT-MachineRegistered`; `journalSinceRegistration(db, machineId)` is what happened to it since.
- **A rule over a whole set** (the museum number, unique among all machines) cannot be arranged in the shared database: such tests use `isolatedTestDatabase(name)` (`src/test-support/isolated-database.ts`) – a database of their own, reset and migrated in `beforeAll`, emptied before each test by the module's test support (`withoutMachines`). The same helper migrates up to a given migration for migration tests.
- **Local browser tests never touch the development database** (ST-083): Playwright starts `scripts/e2e-server.ts`, which creates `laguardia_e2e_test` if missing, resets and migrates it (`resetDatabase` – only names ending in `_test`), creates the e2e technician from `E2E_TEAM_USERNAME` / `E2E_TEAM_PASSWORD` through the Team module's first-technician setup, and only then starts `next dev` on port 3100 with `NEXT_DIST_DIR=.next-e2e` and `DATABASE_URL` / `BETTER_AUTH_URL` set for it – a dev server on 3000 keeps running (Next.js allows one per distDir). Every run starts from the same state: exactly the e2e technician. Local runs use at most 4 workers (`playwright.config.ts`, ST-024): every worker drives the one dev server, and with 8 the longest tests ran into the 30 s timeout. A server already on 3100 fails the run; PostgreSQL not running says `npm run db:up`. `tsconfig.json` includes the `.next-e2e` types `next dev` adds – after a page is removed or renamed, a stale `.next-e2e` (like a stale `.next`) can fail the type check until it is deleted.
- **The QR address `/m/<museum number>`** (ST-010, scheme and domain: `docs/architecture/qr-address.md`, ST-060) is public and never stored by a shared cache: its page reads the request (`headers()`, `cookies()` – the language, with ST-011 the session), so Next.js renders it per request and sends `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` itself. A `Cache-Control` from `next.config.ts` would be overridden – don't add one. `next dev` sends its own header, so the check runs against the preview only. `notFound()` gives 404 only for non-streamed responses, and `not-found.tsx` gets no props. A malformed percent-encoding in the address never reaches a page – Next.js answers 400 itself.
- **The QR sticker's domain** is the constant `QR_DOMAIN` in `src/app/qr-address.ts` (`qrAddress(museumNumber)`) – never the request's host or `VERCEL_PROJECT_PRODUCTION_URL` (ST-011, `docs/architecture/qr-address.md`). A logged-in team member opening `/m/<number>` is redirected to the machine record. Pages made for printing live in the route group `src/app/(print)/` – no team navigation, they check access themselves; the label sheet's millimetres are one `LabelSheet` entry (`L7160`).
- **A second browser context** (a visitor's phone beside the test's own page) needs the preview's protection bypass too: `allowPreview(page, baseURL)` from `e2e/fixtures.ts`, then one navigation before the response under test.
- **Browser tests share their helpers in `e2e/fixtures.ts`** (architecture review 2026-10-11): `logIn(page, account?)`
  (the e2e technician by default), `aHelper(page)`, `aMachine(page, machineStatus?, location?)`, `anOpenDefect(page,
  { suitableForHelpers })`, `openDefect`, `openDefectsEntry`, `unique` / `uniqueId`, `pageWidth`, `TECHNICIAN`. A spec
  defines a helper of its own only for what is particular to it – never a second copy of one of these.
- **Browser tests** must run against the preview too: no reliance on local data, unique texts per run; a page reached with `page.request` needs a navigation first, which sets the preview's bypass cookie. `e2e/security.spec.ts` (CSRF on `/login`) and `e2e/home.spec.ts` need no account and run there.
- Never weaken or delete a test to get green.

## Before a story is done

- [ ] Scenario tests titled exactly, at the seams above; `npm run verify -- --e2e` green
- [ ] Commands via `aggregateCommand` (load → decide → save), IDs from `events.yaml`, journal `data` without free text
- [ ] No `new Date()` / `randomUUID()` in domain code; times via `time.ts`
- [ ] Server Actions only through `formAction` (the one exception: recording the Last visit, ADR 0011); the actor only from `currentPerson()`
- [ ] Texts from the catalogs; new glossary terms in `CONTEXT.md` first
- [ ] Only `index.ts` imported across modules
- [ ] Migration generated and committed when `schema.ts` changed
